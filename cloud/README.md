# Cloud collaboration service

The Worker (`cloud/worker.js`) serves Better Auth identities from D1 (`cloud/auth.js`) and routes the rest of the HTTP API to four kinds of SQLite Durable Objects:

- `DesignRoom` (`cloud/rooms.js`), one per shared room: document, capability links with roles, account members, operation merging, comments, WebSocket presence and frozen public snapshots.
- `AccountDirectory` (`cloud/accounts.js`), a single instance: credentials only. It holds magic-link sign-in, hashed legacy sessions, passkeys, handoffs, the development outbox and a mirror of each account (id, email, handle, name) for passkey ceremonies. Profiles, the room membership index, publications and the app registry live in D1 (`cloud/profiles.js`, see "Account directory in D1").
- `PublishedApp` (`cloud/apps.js`), one per published app: immutable, versioned static builds (file bytes in the `ASSETS_BUCKET` R2 bucket).
- `AiRun` (`cloud/ai-run.js`, code in `cloud/ai-host.js`), one per model API run: hosts the run's executor so it outlives the request that started it, receives cancel and approval notifications, pushes events to subscribed streams, and uses an alarm for lease renewal, approval timeouts and closing a run whose host was reset. Run state stays in D1. See [docs/ai-runtime.md](../docs/ai-runtime.md#hosting).

The same code also runs on Node (`server/node.mjs`, VPS or Docker) through the adapters in `cloud/platform/`: see [cloud/platform/README.md](platform/README.md) for the runtime interfaces and how Durable Object semantics are kept, and [docs/self-hosting.md](../docs/self-hosting.md) to run it. On Vercel (`api/server.mjs`, several stateless instances with libSQL, Redis and S3) it runs through `cloud/platform/vercel/`: see [docs/deployment-vercel.md](../docs/deployment-vercel.md).

Documents are JSON objects or arrays. Version-2 design documents (`pages[].nodes[]`) are stored per page and merge per page, per node and per property; other documents merge per top-level key. Limits are in [`cloud/limits.js`](limits.js) (values in `web/room-limits.js`, which the renderer loads as `window.VerynizeRoomLimits`): `PAGE_BYTES` 2 MiB per page, `DOCUMENT_BYTES` 20 MiB per document (as a desktop file), `META_BYTES` 2 MiB for the top-level fields (and for documents without pages), `REQUEST_BYTES`/`MESSAGE_BYTES` 21 MiB per request body or socket message. Sizes are UTF-8 bytes of JSON.

## Page storage and lazy pages (`cloud/room-store.js`, `web/page-loader.js`)

- **Records.** A room stores its document's metadata (every top-level field except `pages`: name, variables, styles, …) apart from its pages. Each page is one record keyed by its id: a `pages` row (position, size, node count) plus the page's properties (`h:<id>`) and nodes (`n:<id>`) as JSON texts in `parts` rows of at most 256 Ki UTF-16 units (a Durable Object SQLite row holds at most 2 MB). `node_pages` maps node ids to pages. Documents without pages, or with a repeated page id, are one text (`w`). Assembled documents serialize exactly as written (key order is kept).
- **Writes.** An operation batch loads only the pages it names (`VerynizeOps.touchedPages`); the other pages are stubs that are never written back, and `node_pages` keeps node ids unique across them (`apply(..., {external})`). Only the metadata and the pages that changed are rewritten. Legacy whole-document `PUT` writes and `update` messages diff against the stored document and rewrite only the pages that differ. Every write is checked against the limits before anything is stored: a batch over a limit is refused whole (`ops` message with `rejected`, `error` and `tooLarge`; `POST /ops` answers 413), `POST /api/rooms` and `PUT` answer 413.
- **Migration.** Rooms that kept the whole document in `room.document` move to page records the first time the room starts after the upgrade, in one atomic turn; `meta.layout` records it, so it runs once. Stamps, clients, members, links, comments and an existing public copy are untouched (tests/cloud-room-pages.mjs, with tests/fixtures/design-room-whole-document.js).
- **Public copy.** Publishing stores the assembled document as one frozen text (`pub` parts); copies published before the upgrade stay in `room.public_document` until the next publish.
- **Lazy joining.** `GET /api/rooms/:id?lazy=1[&page=<id>]` returns the metadata, every page's properties with `nodes: []` for the pages not sent, `unloaded` (their ids) and `pages` (`[{id,bytes,nodes}]`), with the nodes of the requested page (default: the document's `activePage`, else the first). Sockets opened with `lazy=1` get `welcome {…, lazyPages:true}` and no snapshot; the client answers `sync {pages, revision?}` (the pages it holds) and gets `snapshot {document, revision, acked, unloaded, pages}`, or `snapshot {same:true, revision, acked, pages}` when its revision is current. `pages {ids}` returns one `pages {revision, pages:[page]}` message per page (`missing` lists unknown ids). Pages travel on the socket that carries the operations, so a page includes every operation sent before it. `GET /api/rooms/:id/pages?id=…` is the HTTP form. Clients without `lazy=1` (older apps, the hosted MCP, `GET` without `lazy`) still receive whole documents.
- **Client.** `web/page-loader.js` (`window.pageLoader`) tracks the unloaded pages of the open room. Switching to one (the `web/app.js` render hook) requests it and covers the canvas with `#page-loading` ("Loading page…", or "This page loads when the shared room is reachable." offline). Remote operations on an unloaded page's nodes are dropped (the fetched page contains them); local edits made on a page while it loads, and the removal of a page that has not loaded (so undo can restore its layers), are held (`deferred`), shown on top of the editor document, stored in the outbox and sent when the page arrives. Arriving pages also replace their stubs in collaborative undo steps. The remaining pages are prefetched after 1.5 s of idle (`localStorage['verynize.pages.prefetch']`: `off` or a delay in ms). Whole-document features wait for every page first (`pageLoader.ensureAll()`): Save design / Save as and the web JSON download, saving a document as a template, updating component instances, the desktop MCP bridge's document reads, publishing (pages with held edits), and Disconnect (so the detached copy is complete).

## Merging (`web/cloud-ops.js`, shared by the Worker and the desktop panel)

Each local change is turned into small operations: `doc`, `page`, `node` (property set or delete), `add` and `remove` (node), `addPage` and `removePage`, `nodeOrder` and `pageOrder`, `text` (string edit with its base), and `root` (whole-value fallback). Every operation carries a hybrid logical clock stamp (`wall.count.replica`, compared as a string). The room applies batches in arrival order:

- Each property path keeps the newest stamp, so the last writer wins per property. Stale writes are dropped even when they arrive late or after a restart, because stamps persist in SQLite. Stamps more than five minutes in the future are replaced with a server stamp.
- Text edits made from the same base are merged by range: disjoint edits are both kept, and overlapping edits fall back to the newest stamp.
- A `parentId` change that would create a cycle, or that points at a missing parent, is rejected. After each batch, orphaned children (whose parent was deleted concurrently) are reattached to the page.
- Deleting a node beats concurrent property edits. A newer re-add (undo) restores the node, but an older add cannot resurrect it.
- Each batch is applied at most once per `client` and `batch` number, and the reconnect snapshot reports the last acknowledged batch.

The room broadcasts only accepted, resolved operations (`{type:'ops',revision,client,batch,ops,rejected}`). Replaying them in order reproduces the server document exactly. Each client renders the confirmed server state plus its own unacknowledged batches.

While collaborating, undo and redo step through this client's own changes only (`window.cloudHistory`, which `web/app.js` consults). Each step stores the documents around the local change, and consecutive changes within 600 ms with no remote edit between them form one step. Undo replays the inverse operations rebased over the remote operations received since that step:

- Properties, page and node orders, and nodes that a collaborator changed later are left alone.
- An add is not undone if a collaborator edited that node.
- Text inverses are merged by range into the current text, and are skipped when the ranges overlap.

Redo works the same way.

This is server-sequenced operation merging, not a peer-to-peer CRDT. It needs the room to order batches, and edits made while offline are merged when the socket reconnects.

## Cloud files and offline edits (`web/cloud-panel.js`, `web/wonder-shell.js`)

A room behaves like a file that the desktop and the web editor open:

- **Identity.** A file library record can be cloud-backed: `cloud: {server, roomId, token?, role, detached?}`. The capability token is kept only for rooms joined or created with a link, in the same device-local storage as the record itself. Rooms reached through an account (direct member or organization) store no token and reconnect with the account session. Duplicating a file drops the link.
- **Opening.** Opening a cloud-backed record (`fileLibrary.open`, which emits `library-file-opened`), or starting the app with one as the current file, reconnects to its room. Joining a room (invite, Account › Your rooms, Files home) opens the room's existing record instead of creating another copy; the first join creates it. Create room marks the open file as the room's file. Disconnect, leaving the room and revocation keep the local copy and mark it `detached`; a detached copy that was edited since is left as a separate local file when the room is joined again, and the room gets a new record.
- **Files home.** Signed in with an email account, the Files home lists the rooms of the active workspace (`GET /api/orgs/:id/rooms`) and rooms shared with you directly (`GET /api/me/rooms` entries without an organization), merged with the device's cloud-backed records so a room appears once. Cards carry `data-room-id`, the workspace (or "Shared with you"), a cloud mark and the role. Opening a listed room joins it (`cloudWorkspace.openRoom`).
- **Persistent outbox.** For each room the device stores, in IndexedDB (`verynize-cloud` › `outbox`, key `<server>|<roomId>`), its client id, batch counter, unacknowledged batches, the last confirmed document and revision, and its lazy-page state (`pages: {unloaded, deferred}`). It is written shortly after every queued batch, acknowledgement or remote change, and immediately when the file is switched. Reopening the file (also after a restart) reuses the client id, so the socket's `acked` drops the batches the server already applied and the rest are resent; the server applies each batch at most once per client id. Edits in the file beyond the stored confirmed document and batches (made while the room was closed, or not yet stored when the app quit) are diffed and sent as one more batch. Beyond 4000 operations or about 1.5 MB of batches only the confirmed document is kept, and the file is diffed against it again (whole-document fallback).
- **Offline.** When the server is unreachable, a file with a stored outbox opens offline: edits queue and persist, and the socket keeps retrying (backoff up to 15 s). On reconnect the server snapshot replaces the confirmed document and the pending batches are rebased onto it as usual. A file never opened on the device cannot open offline.
- **Clearing.** Disconnect, leaving the room, revocation (`revoked`, or 401/403/404 when reopening) clear the stored outbox. Signing out keeps the record linked; it reconnects after signing in again.

`window.cloudWorkspace` also exposes `room()`, `openRoom({server,id})`, `pendingCount()`, `pages()` (`{unloaded, requested, deferred}`) and `storedOutbox(server,id)`; `window.fileLibrary` adds `findCloud(server,roomId)`, `cloudOf(id)` and `setCloud(id,cloud)`.

## Share panel: server and invite links (`web/cloud-panel.js`, `web/cloud-invite.js`)

- **Server.** The web app uses its own origin. The desktop (served from `app://verynize`) fills an empty Server URL with `cloudDefaults().server` from `desktop/cloud-defaults.cjs`: `https://verynize.gayaloo.app`, or `VERYNIZE_CLOUD_SERVER` when set. A saved account, the Settings preference or an opened room still take precedence, and the field stays editable. Automated runs (`VERYNIZE_SKIP_ONBOARDING=1`, which every Electron test sets, or `VERYNIZE_BLOCK_PRODUCTION_CLOUD=1`) cancel every editor request to the production host, so tests must point at their local server.
- **Invite links.** An owner's invite never carries the owner's own token. When the panel opens (or on Copy invite), the panel issues a role-limited link with `POST /api/rooms/:id/tokens` (`Editor invite` by default, `Viewer invite` with the "Can view" choice) and shows it in `#cloud-invite`. Each link is stored on the device per room (`localStorage` `verynize.cloud.invites`, `{id, token}` per role) and reused while `GET /access` still lists it; a revoked or rotated link is replaced. The creator's owner token stays private in the file record (`cloud.token`) for reconnecting. Non-owners share the link they joined with (same or lower role), or a token-free link that only opens for account members. Servers without roles (protocol 1) keep their single room token as the invite.
- **Actions by role.** Create room is hidden while a room is open; Publish snapshot and Unpublish are shown to editors and owners only; link management, rotation and members are owner tools (`#cloud-owner-tools`). Publishing still needs only the editor role on the server.

## API

Rooms (capability `Authorization: Bearer <64 hex>` and/or session `X-Verynize-Session: vs_…`):

- `POST /api/rooms` `{document}` → 201 `{id,token,revision:0,role:'owner'}`. With a session, the creator becomes an owner member. Rate limited to 10 per minute per IP. Requests from the web app need a session on every room route (`ROOM_ACCOUNT_REQUIRED`, see "Web sign-in").
- `GET /api/rooms/:id` → `{document,revision,role,protocol:2,title}`. With `?lazy=1[&page=<id>]` only that page holds its nodes, plus `unloaded` and `pages` (see "Page storage and lazy pages").
- `GET /api/rooms/:id/pages?id=<page>[&id=…]` → `{revision,pages,missing}` (any role).
- `PUT /api/rooms/:id` `{document,baseRevision}` (editor) → `{document,revision}`, or 409 `{error,document,revision}`. This legacy whole-snapshot write is still supported, and it stamps its changes so that older operations lose to it.
- `POST /api/rooms/:id/ops` `{client,batch,ops}` (editor) → the ops message. This is the REST fallback when no socket is open.
- `GET /api/rooms/:id/socket?token=…&session=…&client=…[&lazy=1]` upgrades to a WebSocket. The server sends `welcome {id,protocol,role,acked}`, then `snapshot {document,revision,acked}` (with `lazy=1`: `welcome {…,lazyPages:true}`, and the snapshot answers the client's `sync`). Clients send `ops {batch,ops}`, `presence {name,cursor,pageId}`, `sync {pages,revision?}`, `pages {ids}` or the legacy `update {document,baseRevision}`. The server sends `ops`, `snapshot`, `presence {peers}`, `role {role}`, `revoked`, `comment {comment}`, `conflict` (legacy only) and `error`. A room allows at most 32 connections.
- `POST /api/rooms/:id/publish` (editor) → `{publicId,revision}`. It freezes the latest revision, and publishing again rotates the public link. With a session, the design is listed on the creator's profile. `DELETE /api/rooms/:id/publish` revokes public reads and removes the listing. `GET /api/public/:publicId` → `{document,revision}`.
- `GET /api/rooms/:id/access` → `{role,members,title}`. Owners also receive `links` (id, role, label, created).
- `POST /api/rooms/:id/members` `{email,role}` (signed-in owner) adds or changes an account member. An unknown email gets an unverified account, and an invitation is emailed. `DELETE /api/rooms/:id/members/:accountId` removes a member (owners remove anyone; anyone may leave). The last owner account cannot be removed unless an owner link exists.
- `POST /api/rooms/:id/tokens` `{role,label}` (owner) → `{id,token,role}` for a role-limited invite link. `DELETE /api/rooms/:id/tokens/:id` revokes one link.
- `POST /api/rooms/:id/tokens/rotate` (owner) → `{token,role:'owner',revoked}`. Every capability link is deleted and a new owner link is issued. Sockets that relied on a revoked link receive `revoked` and are closed with code 4401. Account members keep their access. An owner account can call this with only its session, which is how a lost owner link is recovered.
- `POST /api/rooms/:id/claim` (owner link plus session) adds the signed-in account as an owner. Rooms created before accounts can be attached to an account this way.
- `GET|POST /api/rooms/:id/comments`: reading needs viewer, posting needs commenter. Comments take `{text,nodeId?,pageId?}`.

Roles are `viewer` < `commenter` < `editor` < `owner`. A request's role is the higher of its capability link's role and its account membership's role. Viewers and commenters can read the room and see presence. Comments need commenter. Edits, snapshots and publishing need editor. Members, links, rotation and claiming need owner.

Accounts:

- `POST /api/auth/start` `{email}` sends a single-use sign-in link (`<origin>/#signin=<64 hex>`) that is valid for 15 minutes. It is rate limited per IP and email.
- `POST /api/auth/verify` `{token,label?}` → `{session:'vs_…',account}`. The account is created on first use. Sessions last 30 days and are stored as SHA-256 hashes.
- `GET /api/me` → `{account,sessions,profilePath,personalOrganizationId,aiSetupAt}`. `PATCH /api/me` takes `{handle?,displayName?,avatarUrl?,aiSetup?}` (`aiSetup` records or clears the web AI setup, "Web sign-in"). Handles are unique, 3–30 characters of `a-z 0-9 -`, and some names are reserved. Avatars must be `https:` URLs. `GET /api/me/rooms` lists the account's rooms and roles.
- `POST /api/auth/signout` ends the current session. `POST /api/auth/signout-all` ends every session of the account.
- Passkeys (original WebAuthn verification in `cloud/webauthn.js`: WebCrypto plus a minimal CBOR/COSE reader; ES256, Ed25519 and RS256; attestation is requested as `none` and never evaluated). The ceremony runs on the server's own `GET /passkey` page (script `/passkey.js`, CSP `script-src 'self'`), and the relying party ID is the request host (`PASSKEY_RP_ID` overrides it).
  - Registration: `POST /api/auth/passkeys/ticket` (session) → `{ticket}` (10 min). The page then calls `register/options {ticket}` → creation options (discoverable credential required, exclude list) and `register/verify {ticket,challenge,credential,label?}`. The checks cover type, single-use challenge, origin, RP ID hash, user presence and credential ID, and the key must import. A successful registration ends all tickets of the account.
  - Sign-in: `login/options {handoff?,email?}` → request options. Without an email, browsers offer the site's discoverable passkeys. With an email, the account's credential IDs are listed; Electron windows need this because they have no passkey chooser. This reveals whether an email has passkeys. `login/verify {challenge,credential}` checks the signature over `authData‖SHA-256(clientData)`, the user handle and a counter that must advance (cloned authenticator).
  - Handoff for other origins: `POST /api/auth/handoff` → `{id,secret}`. The page signs in for that `id`, and the desktop polls `POST /api/auth/handoff/claim {id,secret}`, which returns 202 while pending and `{session,account}` once (single use, 10 min).
  - `GET /api/me/passkeys` lists the account's passkeys and `DELETE /api/me/passkeys/:id` removes one.
- `GET /api/profiles/:handle` returns the public JSON profile (`handle`, `displayName`, `avatarUrl`, `publications`; never the email). `GET /u/:handle` returns the server-rendered profile page. It is escaped, runs no script, and sends a strict CSP.
- `GET /api/dev/outbox?to=<email>` works only when `EMAIL_PROVIDER=outbox` and returns the stored messages. It exists for local development and tests.

Published apps (session required; the app owner only):

- `POST /api/apps` `{name,title?}` → `{app}` (idempotent per account). `GET /api/apps` lists the account's apps. `GET /api/apps/:id` → `{app,versions}`.
- `POST /api/apps/:id/versions` → `{version}`. `PUT /api/apps/:id/versions/:v/files/<path>` uploads raw bytes (25 MB per file, 3000 files and 100 MB per version, 20 sealed versions). Paths are relative; `..`, absolute paths, backslashes and control characters are rejected.
- `POST /api/apps/:id/versions/:v/finalize` `{files:[{path,size,sha256}],activate?}` checks every file against the manifest, requires `index.html`, drops stray uploads, seals the version and (by default) makes it live → `{version,files,bytes,url,versionUrl,app}`.
- `POST /api/apps/:id/activate` `{version}` rolls back or forward. `DELETE /api/apps/:id/versions/:v` deletes a version (the live one is refused). `DELETE /api/apps/:id/publish` unpublishes the app and removes it from the profile while keeping its versions.
- `GET /apps/<handle>/<name>/…` serves the live version, and `GET /apps/<handle>/<name>@<v>/…` serves a pinned version (cached as immutable). Content types follow the file extension. Directory paths resolve to `index.html`, and extension-less paths fall back to the root `index.html` for client-side routes. Responses carry an ETag and `x-verynize-app-version`. HTML gets a `<base href>` for the app root.

Apps are served with `Content-Security-Policy: sandbox allow-scripts allow-forms allow-popups allow-modals allow-downloads`. They therefore run with an opaque origin and cannot read the editor's storage or call the API with its credentials. Assets carry `Access-Control-Allow-Origin: *` so that module scripts load. As a consequence, apps cannot use `localStorage` or cookies. Full origin isolation needs a separate apps domain, which needs a live domain.

The desktop publisher (`desktop/app-publish.cjs`) runs the project's own `build` script and gives Vite/Vite+ builds a relative base. It finds `dist`, `build`, `out` or `public` (or `package.json` `verynize.outputDir`), hashes the files and uploads them four at a time.

## Web sign-in (`web-start`, `cloud/web-access.js`)

The browser app (TanStack Start in `web-start/`, every backend: Cloudflare, Node, Vercel) needs a Verynize account. The desktop app does not: it loads `web/index.html` over `app://verynize`, never this app, and keeps its local-first editor and anonymous sharing.

- **Before the editor.** The editor layout (`web-start/src/routes/_editor.tsx`) checks the stored session for this origin (`verynize.cloud.account`, the record `web/cloud-panel.js` reads) with `GET /api/me` before it boots the legacy editor (`web-start/src/legacy/web-auth.ts`). A rejected session (401/403) is dropped; an unreachable server keeps it, so a signed-in browser still opens offline. Without a session every editor path (`/`, `/editor`, `/code`, `/settings/*`) renders the sign-in screen (`web/src/islands/onboarding/web-sign-in.tsx`): the desktop onboarding's account form bound to this server (`web/src/lib/web-session.ts`) with email + password sign-in, sign-up (verification email), forgot password, and passkey sign-in through `/passkey` and a handoff. No legacy script runs until then. The address is left alone, so after signing in the editor boots at the requested path with its fragment, and `#room=…&token=…` invites and `#invitation=…` links work as before. `<html data-web-auth>` is `checking`, `signed-out`, `signed-in` or `public`. Signing out (Share › Account, Settings) reloads the page into the sign-in screen. The legacy emailed sign-in links (`#signin=`) are not handled: no current client sends them.
- **Public surfaces stay anonymous**: published snapshots opened in the editor (`/#public=…`, `data-web-auth="public"`, `GET /api/public/*`), profiles (`/u/*`), published apps (`/apps/*`), `/passkey`, `/account/*` pages and static assets. `/api/*` keeps its own rules (below).
- **Server side.** `ROOM_ACCOUNT_REQUIRED` (text variable; `cloudflare.config.ts` sets `web`, which is also the default when unset; the Node and Vercel servers read it from the environment):
  - `web`: a request from the web app needs a signed-in account (session header, or `?session=` on sockets) on every room route: `POST /api/rooms`, `GET|PUT /api/rooms/:id`, `/ops`, `/access`, `/comments`, `/publish`, `/tokens`, `/members`, `/claim`, `/organization` and the socket. Otherwise 401 `{"error":"Sign in to Verynize first"}`. "From the web app" means `Sec-Fetch-Site: same-origin` (browsers send it on every request, sockets included) or an `Origin` equal to the server's origin. The desktop renderer is cross-site (`Origin: app://verynize`) and scripts send neither, so they keep anonymous rooms and capability-link joins. This is a rule for the web client, not an access control against scripts: anyone can create anonymous rooms the way the desktop does.
  - `all`: as `web`, and creating a room needs an account from any client. It closes anonymous room creation for scripts too, but the desktop's "Create room" then fails until it signs in (invite joins keep working). Not enabled in production for that reason.
  - `off`: the behaviour before web sign-in.
  - Room assets (`/api/rooms/:id/assets*`: editor role or a signed URL), `/api/public/*`, `/api/auth/*`, `/api/me*` and the other account routes keep their own rules.
- **AI setup after the first sign-in.** The onboarding island (`web/src/islands/onboarding.tsx`, web branch) opens "Set up your AI" when `GET /api/me` reports `aiSetupAt: null`: connect OpenRouter (OAuth in the tab or a pasted key, `cloud/ai.js` credential routes, the same controls as the chat gate) with live connected/not-connected status, Claude Code and Codex shown as desktop-only, "Skip for now", then a summary. Finishing or skipping sends `PATCH /api/me {"aiSetup": true}`, which stores `profile.aiSetupAt` (migration `0008_profile_ai_setup.sql`; `{"aiSetup": false}` clears it), so the steps show once per account on any browser; a per-account localStorage copy covers a failed request. Settings › Agents › Model API › AI setup › Open setup reopens them.

Tests: `node tests/cloud-web-access.mjs` (the server rule in all three modes, sockets, invite links, public snapshots, the `aiSetup` flag), `node tests/web-cloudflare.mjs` (sign-in screen, sign-up, password sign-in keeping path and invite fragment, AI setup opening, anonymous public snapshot; `vp dev` and `vp preview`), `node tests/web-ai-chat.mjs` (Node build with the real backend: sign-in, AI setup once per account, skip, reopen from Settings, connected state, sign out) and `node tests/web-node.mjs`.

## Better Auth on D1 (`cloud/auth.js`)

Email + password accounts and organizations run on [Better Auth](https://better-auth.com) with the `DB` D1 binding. The schema lives in `cloud/migrations/*.sql`; `node scripts/auth-schema.mjs` prints the SQL for the current options, which is the starting point for a new migration after changing plugins or fields. The desktop signs in with email + password (Share › Account: Sign in, Create account, Forgot password). Profiles, the room index, publications and apps are in D1 (below); passkeys keep their own `vs_…` sessions.

- Every Better Auth endpoint is served under `/api/auth/*`, after the legacy account routes (their paths do not overlap). The main ones are `POST sign-up/email {email,password,name}`, `POST sign-in/email {email,password}`, `GET get-session`, `POST sign-out`, `POST request-password-reset {email,redirectTo}`, `POST reset-password {token,newPassword}`, `GET verify-email?token=…` and `POST send-verification-email`, plus the organization plugin under `organization/*` (`create`, `list`, `get-full-organization`, `invite-member`, `accept-invitation`, `update-member-role`, `remove-member`, …).
- Passwords are 10–128 characters and hashed with Better Auth's default scrypt. Email verification is required before sign-in. A password reset revokes every session of the account. Reset, verification and organization invitation emails go through `cloud/mail.js` (invitation links are `<origin>/#invitation=<id>`).
- Sessions last 30 days and travel only as bearer tokens: sign-in returns the token in the body and in the `set-auth-token` response header, and clients send `Authorization: Bearer <token>`. The Worker drops request `Cookie` and response `Set-Cookie` headers, so there are no ambient credentials, and Better Auth's cookie CSRF check is disabled (it refuses the `Origin: null` sent by the desktop's `file://` renderer). Redirect and callback URLs are still validated against trusted origins. Responses carry the desktop CORS headers and expose `set-auth-token`.
- `sign-up/email`, `sign-in/email`, `request-password-reset`, `reset-password`, `send-verification-email` and `change-password` are limited by `AUTH_LIMIT` per IP and endpoint. Better Auth's own limiter is off because it keeps state in isolate memory.
- **Bridge to directory accounts.** Every API that takes a session (`X-Verynize-Session`, `Authorization: Bearer` or the socket's `?session=`) accepts either a legacy `vs_…` session or a Better Auth token. A Better Auth user acts through the directory account with the same email (`linkVerifiedAccount`): it is created when missing (display name from the sign-up name), and an account made earlier by a magic link or an email invitation is linked and marked verified. This is safe because Better Auth only signs in verified addresses and does not allow email changes. Room roles, invitations by email, profiles, passkey registration and apps therefore work unchanged.
- `POST /api/auth/signout` ends the Better Auth session it is called with (or the legacy session). `POST /api/auth/signout-all` revokes every Better Auth session of the user and every directory session of the linked account. `GET /api/me` counts both.
- Emailed links land on Worker pages (`cloud/account-pages.js`). Clients pass `callbackURL: "/account/verified"` to sign-up and sign-in, and `redirectTo: "/account/reset-password"` to `request-password-reset`. `/account/verified` runs no script. `/account/reset-password` loads only `/account/reset-password.js` (CSP `script-src 'self'`), which drops the token from the address bar and posts `reset-password`. An unverified sign-in (403 `EMAIL_NOT_VERIFIED`) emails a fresh verification link.
- The legacy magic-link routes (`/api/auth/start`, `/api/auth/verify`) remain for older desktop builds; the current desktop no longer offers them.
- `BETTER_AUTH_SECRET` signs tokens. `AUTH_URL` (optional) overrides the origin used in emailed links, which otherwise is the request origin.

## Account directory in D1 (`cloud/profiles.js`)

Migration `0003_directory.sql` adds `profile`, `room_membership`, `publication`, `app` and `migration_state`. Account ids are the former `AccountDirectory` ids, so room members, live sockets and app versions keep their references.

- A **profile** is the public account: email, handle, display name, avatar and `verified`. `userId` links it to its Better Auth user. Better Auth sessions resolve through that link, or on first use through the verified email, which also links profiles made earlier by a magic link, a passkey or an invitation. Legacy `vs_…` sessions resolve to an account id in `AccountDirectory`, then to its D1 profile.
- Magic links (`/api/auth/start`, `/api/auth/verify`) still work for older desktop builds. The link is consumed in `AccountDirectory`, the profile is created or found in D1, and the session is issued for its id. Creating a passkey ticket and editing a profile refresh the account's mirror in `AccountDirectory`.
- **One-time copy.** The first request to `/api/*`, `/u/*` or `/apps/*` after the upgrade copies `accounts`, `memberships`, `publications` and `apps` from `AccountDirectory` into D1 (`migrateDirectory`). Progress is recorded in `migration_state` (`running`, `done` or `failed`; a run stuck for 5 minutes is taken over), and each isolate checks it once. The copy is idempotent:
  - an email that already has a D1 profile keeps it, and the old account's rows are mapped onto it;
  - a handle that is already taken is replaced by a free one;
  - re-running adds nothing.

  The old tables stay in `AccountDirectory`, unused.

- **Adopting old rooms.** The first email + password sign-in of an account that existed before moves the rooms it owns that are not in any organization into the user's personal organization.

## Organizations and room access (`cloud/orgs.js`)

Rooms created by an email + password user belong to a Better Auth organization, recorded in the D1 `room` table (`cloud/migrations/0002_rooms.sql`). The document stays in the room's Durable Object. Rooms created with a legacy session, or without signing in, stay outside organizations until an owner moves them.

- **Personal organization.** Each user has one, created on first use (`GET /api/me` returns `personalOrganizationId`; `POST /api/rooms` without `organizationId` uses it). Its slug is `personal-<user id>`, and its metadata carries `personal: true`. Other organizations cannot use that slug prefix or set the marker, and metadata updates keep the marker as it is.
- **Room role from the organization.** Owners and admins of the organization become room owners. Members get the organization's `metadata.roomRole` (`viewer`, `commenter` or `editor`; the default is `editor`). A request's role is the highest of its capability link, its direct room membership and its organization role. The router computes the organization role from D1 and forwards it as `x-verynize-org-role`; a client-sent header of that name is dropped.
- **Live changes.** Adding a member, accepting an invitation, removing a member, changing a member role, changing `roomRole` and leaving the organization all update the live sockets of the affected rooms (`DesignRoom.applyOrgRoles`). The update sends `role` messages, or `revoked` followed by a close with code 4401.
- `POST /api/rooms {document, organizationId?}` creates the room in an organization the caller belongs to (403 otherwise; 401 for legacy sessions). The response includes `organizationId`.
- `PUT /api/rooms/:id/organization {organizationId}` moves a room. The caller must be a room owner and a member of the target organization. It also attaches legacy rooms to an organization.
- `GET /api/orgs/:id/rooms` (members) → `{role, rooms:[{id,title,createdAt,updatedAt}]}`. `GET /api/me/rooms` merges direct memberships with organization rooms (`organizationId`, `organizationName`), keeping the higher role. `GET /api/rooms/:id/access` adds `organization {id,name}`.
- An organization that still has rooms cannot be deleted (409). Titles listed from D1 follow the room's title whenever a room response reports it.
- Better Auth endpoints also accept the session in `X-Verynize-Session`, so the desktop sends one header everywhere.
- **Desktop UI (phase 3).** Files › workspace switcher lists the account's organizations (personal first), creates organizations and opens Settings › Members. Settings › Members handles invitations, roles, the default member room access (`metadata.roomRole`), invitations addressed to you, leaving and deleting. Share › People & access shows the room's workspace and lets owners move it. Rooms created from the Share panel go to the active workspace. The first-run onboarding signs in or creates the account (default server `https://verynize.gayaloo.app`, changeable) before the agent setup. Tests: `tests/desktop-onboarding.mjs`, `tests/desktop-workspaces.mjs`.

## Hosted MCP (`cloud/mcp.js`)

`POST /api/mcp` is a headless MCP server: agents read and edit the account's rooms without any editor open, and open editors receive the edits through the normal room sync (`ops` messages over the socket).

- **Transport.** The stateless JSON subset of MCP Streamable HTTP: `initialize`, `notifications/initialized` (and other notifications, answered `202` with no body), `ping`, `tools/list`, `tools/call`. Each POST gets one `application/json` response; JSON-RPC batches are answered as arrays. There is no SSE stream and no `Mcp-Session-Id`: `GET`/`DELETE` return `405` with `Allow: POST`. Protocol versions `2025-11-25`, `2025-06-18`, `2025-03-26` and `2024-11-05` are accepted; an unknown `MCP-Protocol-Version` header is a `400`. Requests with a foreign `Origin` header are refused (`403`). Bodies are limited to 8 MB.
- **Auth.** `Authorization: Bearer <session token>` or `X-Verynize-Session: <session token>`, resolved exactly like the rest of the API: a Better Auth bearer token (the `set-auth-token` header of `POST /api/auth/sign-in/email`, also what the desktop stores) or a legacy `vs_` session. Anything else, including room capability links, gets `401` with `WWW-Authenticate: Bearer realm="verynize", error="invalid_token"`. There is no OAuth flow yet, so clients must be configured with the header. `MCP_LIMIT` (240 requests per minute) limits per IP and per account; room creation also counts against `ROOM_CREATION`.
- **Tools.** The tool table of `integrations/design-tools.mjs` with the same names, descriptions and schemas, run against a cloud backend (31 tools): `get_design_context`, `get_artboards`, `get_element_tree`, `get_element_code`, `find_elements`, `create_artboard`, `update_elements`, `duplicate_elements`, `delete_elements`, `rename_elements`, `finish_artboard`, `get_design_guidelines`, `get_skills`, `get_icons`, `search_images`, `apply_style_tokens`, `get/create/update/delete_design_tokens`, `bind_variables`, `list_documents`, `open_document`, `create_document`, `create_page`, `rename_page`, `read_document`, `apply_operations`, `export_css`, `export_jsx`, `import_jsx`. Absent from `tools/list` (a call returns an `isError` result that says why): `take_screenshot` (no renderer), `ask_agent`, `import_html`, `export_document`, the design-preference tools and the desktop shell tools. Results carry `_meta: {"verynize/headless": true}`, and backend results report `headless: true` / `live: false`.
- **Documents are rooms.** `list_documents` returns the rooms `GET /api/me/rooms` lists (direct memberships plus organization rooms, higher role wins) with `role`, `organizationId` and the editor URL `<origin>/#room=<id>`. The `document` (or `name`) argument is a room id; it may be omitted when the account reaches exactly one room. `create_document {title, organizationId?}` creates a room with an empty version 2 document like `POST /api/rooms` (personal organization by default, D1 `room` row and membership index; `name` is accepted and ignored). `open_document` only returns the editor URL. `finish_artboard` always reports `unverified` (no screenshot) and focuses nothing.
- **Writes.** A tool's pure transform runs on the room snapshot (`DesignRoom.agentRead`), the result is validated with `validateDocument`, diffed with `VerynizeOps.diff` and sent to `DesignRoom.agentApply`. That RPC recomputes the caller's role from the room membership and the organization role the Worker computed (no capability links), refuses viewers and commenters, refuses a stale base revision so the Worker recomputes the edit (up to five attempts), and applies the batch through `applyBatch` as client `mcp-<account id>`, stamped by the server clock, then broadcasts it like any client batch. Revisions shown to tools are SHA-256 digests of the document, so `apply_operations` keeps its revision check. Remote `<img src="https://…">` photos are downloaded and embedded before the response (up to 512 KB each; a room page holds at most 2 MB).
- **Engine in the Worker.** `cloud/mcp-env.js` bundles what the engine reads from `node_modules` on disk: the Tailwind v4 theme stylesheet (handed to `integrations/tailwind-engine.mjs` as `globalThis.__verynizeTailwindTheme`) and the three Iconify sets (loaded on first use and passed to `provideIconSets`). The router imports `cloud/mcp.js` dynamically, so other routes do not load the engine. The bundle grows from about 0.45 MB to about 2.2 MB gzip (11 MB uncompressed, most of it the icon sets).

Setup for agents (replace the server and the token; `claude mcp add` syntax checked against the installed Claude Code CLI):

```sh
# A session token: the set-auth-token response header of a password sign-in.
curl -si https://verynize.gayaloo.app/api/auth/sign-in/email -H 'content-type: application/json' \
  -d '{"email":"you@example.com","password":"…"}' | grep -i set-auth-token

# Claude Code
claude mcp add --transport http verynize https://verynize.gayaloo.app/api/mcp \
  --header "Authorization: Bearer <token>"
```

Codex (to verify against your Codex version; Codex was not installed where this was written), in `~/.codex/config.toml`:

```toml
url = "https://verynize.gayaloo.app/api/mcp"

```

Session tokens expire with the Better Auth session and are revoked by sign-out; treat them like passwords. Tests: `node tests/cloud-mcp.mjs`.

## Model API runtime (`cloud/ai.js`)

`/api/ai/*` runs a chat turn against an OpenRouter model (TanStack AI `@tanstack/ai` + `@tanstack/ai-openrouter`, pinned to 1.0.1) with the Verynize design tools of one room. The contract (events, policy, clients) is [docs/ai-runtime.md](../docs/ai-runtime.md). All endpoints need a signed-in account (same auth as Hosted MCP); browser requests from another origin get 403.

- `GET /api/ai/config` → `{enabled, provider: "openrouter", models: [{id,label}], defaultModel, limits: {maxTurns, maxToolCalls}, credentials: {openrouter: "connected"|"server"|"missing"}}`. `enabled` is true unless `VERYNIZE_AI=off`; each account brings its own OpenRouter key (`credentials`).
- Credentials (per account, never returned): `GET /api/ai/credentials` → `{openrouter: {connected, source, last4, label, state, limit?, usage?, …}}`; `PUT /api/ai/credentials/openrouter` `{apiKey}` (checked with OpenRouter's `GET /key`; 400 `invalid_key`); `DELETE /api/ai/credentials/openrouter`; `POST /api/ai/credentials/openrouter/oauth/start` `{returnTo?}` → `{authorizeUrl}` + HttpOnly cookie; `GET /api/ai/credentials/openrouter/oauth/callback?code=&state=` (OpenRouter OAuth PKCE; authenticated by the one-time pending state bound to the account and the browser cookie) → 303 to a same-origin path. Keys are stored AES-GCM encrypted in `ai_credential` under a key derived (HKDF-SHA256) from `BETTER_AUTH_SECRET`; pending sign-ins in `ai_oauth_state` (migration `0007_ai_credentials.sql`, `cloud/ai-credentials.js`). `OPENROUTER_API_KEY` is used only with `VERYNIZE_AI_SERVER_KEY=1`, for accounts without a key. Details: [docs/ai-runtime.md](../docs/ai-runtime.md#credentials).
- `POST /api/ai/runs` `{chatId, roomId, prompt, model?, access?, plan?, helper?, history?, designStyle?, idempotencyKey}` → `text/event-stream`, one `data: <event JSON>` per message (comment lines `: keep-alive` every 15 s). 503 when disabled, 409 `{code: "credentials_required"}` when the account has no OpenRouter key, 400 for invalid input, 403 without access to the room, 409 when the chat already has a running turn, 429 for `AI_LIMIT` (20 new runs per account per minute) or more than three running turns per account. A repeated `idempotencyKey` replays the stored run instead of starting another.
- `GET /api/ai/runs/:id/events?after=<seq>` → the stored events after `seq`, then new ones until `done`. A running run hosted by an `AiRun` object streams from the object (live, no polling); otherwise (finished runs, Vercel) the database is polled every 400 ms, so the run may execute on another instance. A running run whose lease expired is closed with `error` + `done {code: "error"}`.
- `POST /api/ai/runs/:id/cancel` → `{ok: true}`; the run's `AiRun` object is notified and the run ends at once with `done {code: "cancelled", stopped: true}` (request-scoped runs on Vercel see the flag within a second).
- `POST /api/ai/runs/:id/approvals` `{requestId, allow, argsHash}` (`argsHash` from the `permission-request`; required to approve) → `{ok: true}`, 400 (bad body, or approving without `argsHash`), 404 (unknown run or request), 403 (another account's run or request), 409 (already decided, the run has ended, or `argsHash` does not match the pending call).

Run, event, approval and tool-result rows live in `env.DB` (migrations `0005_ai_runs.sql` and `0006_ai_approval_account.sql`; `cloud/ai-store.js`). The executor (`cloud/ai-executor.js`) offers the hosted tools of `cloud/design-backend.js` (the backend `cloud/mcp.js` uses, scoped to the run's room; `create_document` is not offered), re-checks the caller's room role before every tool call and again immediately before a write runs, counts tool calls against `maxToolCalls`, caps model turns with `maxIterations(maxTurns)` and stores each event before sending it. Under `access: "ask"` (default) every write waits for a decision stored in `ai_approval` (stored in the database, so the decision may arrive on any instance; the endpoint then notifies the run's `AiRun` object, and request-scoped runs poll), denied after `VERYNIZE_AI_APPROVAL_TIMEOUT_MS` (10 minutes) or when the run ends; `edit`/`auto`/`full` write without a prompt. A write is claimed in `ai_tool_result` before it runs, so it is applied at most once per `(runId, toolCallId)`. `plan: true` refuses write calls; `helper: true` offers no write tools. Optional variables: `OPENROUTER_BASE_URL` (tests point it at a local fake), `VERYNIZE_AI_MODELS` (`id[=Label],…`, first is the default; default `openrouter/auto`), `VERYNIZE_AI_MAX_TURNS` (12), `VERYNIZE_AI_MAX_TOOL_CALLS` (40), `VERYNIZE_AI_APPROVAL_TIMEOUT_MS` (600000). Hosting: Cloudflare and Node run each run in its `AiRun` object (`AI_RUNS` binding); Vercel runs it inside the starting request. Tests: `node tests/cloud-ai.mjs`, `node tests/cloud-ai-durable.mjs` (disconnect, late approval, timeout, cancel and concurrent subscribers; both also on Node and Vercel) and `node tests/ai-routing.mjs`.

## Room assets (`cloud/assets.js`, `cloud/inline-binaries.js`, `web/cloud-assets.js`)

Binary data never lives inside a shared document. Images, SVG, fonts and video in shared rooms are stored once in the `ASSETS_BUCKET` R2 bucket (named so that it does not clash with the static `ASSETS` binding) and referenced from the document by URL. Collaborators therefore receive a short URL operation instead of a data URI, and binaries do not count against the room's document size. Metadata lives in D1 (`room_asset`, migration `0004_room_assets.sql`: room, sha256, size, content type, status, creator, created and uploaded times). Objects are keyed `rooms/<roomId>/<sha256>`. Which data URIs count as binaries comes from one module shared by the editor, the islands and the server: `web/storage-limits.js` (`ASSET_LIMIT_BYTES` 20 MiB, `INLINE_LIMIT_BYTES` 8 KiB, `SVG_INLINE_LIMIT_BYTES` 256 KiB). The page and document limits it reports (`PAGE_LIMIT_BYTES` 2 MiB, `DOCUMENT_LIMIT_BYTES` 20 MiB) are read from `web/room-limits.js`, the values the room enforces (`cloud/limits.js`, "Page storage and lazy pages" above).

- `POST /api/rooms/:id/assets` `{contentType,size,sha256}` (editor) → 201 `{id,url,uploadUrl,method:'PUT',expiresAt,existing:false}`. When the room already holds those bytes (same sha256), the answer is 200 `{id,url,existing:true}` with no upload. Types are `image/png`, `image/jpeg`, `image/webp`, `image/gif`, `image/avif`, `image/svg+xml`, `font/woff2`, `font/woff`, `font/ttf`, `font/otf`, `video/mp4` and `video/webm` (415 otherwise); sizes are 1 byte to 20 MB (413); a room holds at most 2000 assets (507). Rooms never share assets, even for identical bytes.
- `PUT <uploadUrl>` (raw bytes, no credentials) stores the file. The URL is `/api/rooms/:id/assets/:assetId?expires=<ms>&signature=<hex>`: an HMAC-SHA256 under `ASSET_SIGNING_SECRET` over the room, asset, sha256, size, content type and expiry, valid for 10 minutes. A forged, altered or expired URL gets 403; a body that is longer than declared gets 413; a body of a different length or hash gets 400; bytes that are not the declared type get 415 (magic numbers; SVG must be UTF-8 text whose root element is `<svg>`, so HTML declared as SVG is refused).
- `GET|HEAD /api/rooms/:id/assets/:assetId?sig=<hex>` serves the file with its content type, `X-Content-Type-Options: nosniff`, `Cache-Control: private, max-age=31536000, immutable`, an ETag (sha256, so `If-None-Match` gets 304), `Content-Security-Policy: default-src 'none'; sandbox` (SVG additionally allows inline styles and `data:` images and fonts, never script or network loads), `Content-Disposition: inline`, `Cross-Origin-Resource-Policy: cross-origin` and the CORS headers (fonts load across origins). Without `sig`, the request needs room access (viewer or higher, through a capability token or session header, exactly as `/access` computes it): 401 otherwise.

**Inline binaries on the server (`cloud/inline-binaries.js`).** A data URI of a binary type (image, font, video, audio, PDF, octet-stream) longer than 8 KiB is never stored in a room. SVG stays inline up to 256 KiB (icons and recolourable SVG need their source). Text content (`text`, `name`, `description`, `css`) is never treated as binary.

- Room creation (`POST /api/rooms`), snapshot writes (`PUT /api/rooms/:id`), HTTP batches (`POST /api/rooms/:id/ops`) and hosted MCP / model API edits (`cloud/design-backend.js` `transact`) store such data URIs as assets of the room (deduplicated by sha256) and write the asset URL instead. Writes are checked for the editor role first; a viewer's body is forwarded unchanged and refused by the room. A type rooms cannot store gets 413, bytes that are not what the data URI declares 415, a file over 20 MB 413.
- WebSocket batches reach the room directly. There, an operation carrying a large inline binary is rejected with the reason `Inline … data larger than 8 KB cannot be stored in a room; upload it as a room asset first` (the rest of the batch applies). Room creation and snapshot writes are checked the same way inside the room as a backstop.
- Rooms created before this rule are migrated lazily, page by page: when a room is opened (`/socket` and `GET /api/rooms/:id` scan every page, `GET /api/rooms/:id?lazy=1` the pages it loads, `GET /api/rooms/:id/pages` the requested pages), the Worker asks the room for the pages (and document metadata) whose stored text may hold a large inline binary (`DesignRoom.inlineSnapshot`: a page found clean is not rescanned while the room stays active, one that cannot be migrated is offered once per revision), stores those binaries as assets and applies the URL swap as one server batch through the per-page write path (`DesignRoom.migrateInline`, client `server-assets`, broadcast as `ops`). A failed migration leaves the room unchanged and is retried after the next edit or restart. Published snapshots are frozen copies and keep what they held.
- Servers without asset storage (no `ASSETS_BUCKET` or `ASSET_SIGNING_SECRET`) keep the previous behaviour: nothing is extracted or rejected. Asset URLs are only written for origins the schema accepts (https, or http on loopback).

Published apps (`cloud/apps.js`) store the bytes of every file in the same bucket under `apps/<app>/<sha256>` (one object per distinct file, shared by versions); the app object keeps only the version and file index, and deleting a version deletes the objects no other version uses. Files stored before this change, and servers without the bucket, keep 1 MB SQLite chunks.

**Read authorization.** `<img>` elements cannot send headers, so the URL stored in documents carries a read signature: `sig` is an HMAC over the room and asset id, with no expiry. The signed URL is a capability for that one immutable image. It only appears inside the room document, so people who never had room access cannot obtain it, the bare URL without `sig` needs room access, and a signature is bound to its room and asset. The tradeoffs: anyone who once read the document (a removed member, or anyone holding a published snapshot) can keep loading the images they saw, rotating room links does not revoke image URLs, and a leaked URL exposes that image (but nothing else). Short-lived read URLs or `?token=` queries were rejected because the document is shared state: every collaborator and every export would need its own rewritten URL, and expiring URLs would break the stored document. Rotating `ASSET_SIGNING_SECRET` invalidates every stored image URL, so treat it as long-lived.

**Published snapshots.** A published snapshot is a frozen copy of the document, so it holds the same signed URLs, and anonymous viewers of `/api/public/:publicId` can load its images without further grants. Unpublishing revokes the snapshot document, not the image URLs.

**Client.** `web/cloud-assets.js` (`window.cloudAssets`) runs while the editor is connected to a room as an editor or owner. Before `web/cloud-panel.js` sends local operations, it asks `cloudAssets.hold(doc, resume)`. When the open page has embedded binaries (raster image sources of any size, and image fills, image masks and SVG above the inline limits), these are hashed, registered and uploaded, local operations (and the application of remote state) wait until the uploads settle, and the data URIs are replaced through `window.design.updateNodes`. The data URI therefore never reaches the room. Embedded binaries already in a document are swept on connect, on page switches and after remote edits. A failed upload (offline, too large, server without assets) leaves the data embedded; the server then rejects it over the socket and the editor shows the reason. Every insertion path (image tool, drop and paste in `web/image-drop.js`, Figma import, generated images, HTML import, web capture, agents) produces embedded data URIs and goes through this. **Creating a room** (`cloudAssets.createRoom`, called by `#cloud-create`) checks the size limits first (`storageLimits.assertShareable`: nothing is sent when a page or the file is over its limit or an embedded file is over 20 MB), creates the room with 1×1 stand-ins for the large binaries (nobody else knows the room yet), uploads each binary (fonts included) with progress in the Share panel, then writes the real document with the asset URLs (`PUT`, revision-checked) and connects. Retrying after a failed upload reuses the half-created room. A server without asset storage (503) gets the document as before. `cloudWorkspace.room()` and `cloudWorkspace.request()` expose the connected room to this module. `validate()` in `web/app.js` and `validateDocument` in `integrations/design-store.mjs` accept asset URLs of exactly this form for image sources, image fills, image masks and embedded fonts: `https:` (or `http:` on loopback), no credentials or fragment, the path `/api/rooms/<uuid>/assets/<uuid>` and an optional `?sig=<64 hex>`. A half-transparent image fill with an asset URL renders through `-webkit-cross-fade` (an SVG wrapper cannot load remote images).

**Size limits in the editor.** `web/storage-limits.js` measures the open document after edits settle (debounced, never per pointer move) with binaries that will become assets counted as their URL. The storage island (`web/src/islands/storage*`) shows the size in the Share panel (`#storage-meter[data-level=ok|warn|over]`: file size against 20 MB, the largest page against 2 MB, embedded files that will be stored separately, upload progress), a warning from 80 % of a limit naming the page (with a toast), and a blocking error when a share, sync or save is stopped by a limit (`#storage-limit-error` inside the Share panel, `#storage-limit-dialog` elsewhere, titled after the action). Server refusals for size (`exceeds`, `too large`, inline data, 413) reach the same error through the panel's status line, and a native save refused by the 20 MiB file limit of `integrations/design-store.mjs` through `web/desktop-panel.js`.

**Exports and offline use.** Raster and PDF exports (`exportArtwork` PNG/JPG/WebP, and the Export panel's raster and PDF formats in `web/src/islands/inspector/export.ts`) call `cloudAssets.inlineHtml`, which replaces asset URLs (images and fonts) with data URIs, because the offscreen renderer loads no network URLs. HTML exports keep the signed URLs, which load wherever the server is reachable. Raster exports reuse the original data URI of images this client uploaded, so they work offline. The editor renders asset URLs from Chromium's HTTP cache when offline (immutable responses). An image that was never loaded on this machine cannot render offline. The main window has no CSP that blocks remote images. The MCP `take_screenshot` path does not inline room images yet, the SVG export and file thumbnails show only embedded images, and HTML exports opened outside Chromium do not apply the opacity of half-transparent asset image fills (`-webkit-cross-fade`).

## Email delivery (`cloud/mail.js`)

`EMAIL_PROVIDER` selects the transport. `cloudflare` sends through the `EMAIL` send-email binding from `EMAIL_FROM` (what `cloudflare.config.ts` uses). `smtp` (Node server) sends through `SMTP_MAILER`, an SMTP transport with the same `send` shape, from `EMAIL_FROM`. `outbox` stores messages for `/api/dev/outbox` (tests and local development only). `webhook` POSTs `{to,subject,text}` to `EMAIL_WEBHOOK_URL` with `Bearer EMAIL_WEBHOOK_TOKEN`, so that a relay you operate sends the mail. Any other value disables email sign-in with a 503. The webhook relay needs its own live credential and has not been exercised. Invitation emails are best effort, and a failed delivery never blocks the membership change. Passkeys work without email delivery.

## Security notes

Capability tokens, sign-in links and sessions are random 32-byte values. Only their SHA-256 digests are stored. Room UUIDs alone grant no access. The router drops client-supplied identity headers and forwards only the session-resolved account. WebSocket tokens and sessions travel as query parameters, so do not log complete sensitive URLs. CORS permits capability- and session-bearing desktop requests without cookies.

Rooms created by the previous snapshot-only Worker are migrated in place. Their single token becomes an owner link (`tests/fixtures/cloud-worker-v1.js` is that Worker, kept for the migration test). Snapshot-only clients keep working beside operation clients. The desktop panel falls back to the snapshot protocol, with its conflict prompt, when a server does not report `protocol: 2`.

## Configuration and deployment

`cloudflare.config.ts` enables `nodejs_compat` (Better Auth imports `node:async_hooks`), raises the CPU limit to 30 s per invocation (Workers Paid, for scrypt), and declares the `DB` D1 database, the `BETTER_AUTH_SECRET` secret, the `ASSETS_BUCKET` R2 bucket and its `ASSET_SIGNING_SECRET` secret (room assets), the four SQLite Durable Object classes (`AiRun` is new: `cf deploy` applies its migration from the `exports` declaration), four rate limits (`ROOM_CREATION`, `AUTH_LIMIT`, `MCP_LIMIT`, `AI_LIMIT`), `ROOM_ACCOUNT_REQUIRED=web` (web sign-in), the email variables and Worker-first routing for `/api/*`, `/u/*` and `/apps/*`. Vite serves the web static assets. Deploy only through `npm run deploy` (`cf deploy`). This implementation has only been built and tested locally (`npm run deploy:check` is a dry run), not deployed. Before a public deployment, it still needs account quotas beyond the per-account app limit, room deletion and lifecycle, abuse reporting for public profiles and apps, and a dedicated apps origin.

## Drizzle ORM on D1

`db.js` constructs a request-scoped Drizzle D1 client. `schema.js` maps the eight existing D1 tables (Better Auth plus the organization room index). Better Auth uses its Drizzle adapter with SQLite and interactive transactions disabled for D1. Organization queries use the query builder and parameterized `sql` templates for joins. Durable Object storage remains independent.

Existing SQL migrations in `cloud/migrations` remain authoritative and are applied by `npm run db:migrate`; this adapter change requires no new migration. Auth date fields deliberately use ISO text mappings, preserving the original adapter's stored values in SQLite `date` columns; room timestamps stay epoch milliseconds. Do not regenerate those fields as integer timestamps without a separate data migration.

When changing auth plugins or fields, use `scripts/auth-schema.mjs` as a reference for Better Auth's required SQL, review an incremental SQL migration (never replay the initial CREATE TABLE statements), and update `cloud/schema.js` to match. The generator intentionally uses the native SQLite adapter only for schema discovery. It is not the runtime database adapter. No Drizzle Kit push or remote credentials are needed for this integration.

Validation: `npm run test:cloud` covers old-format session reads/expiry/revocation, new account flows, room permissions, and restart persistence; `npm run deploy:check` validates Worker packaging without uploading.
