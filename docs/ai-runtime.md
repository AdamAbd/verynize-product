# Model API runtime (TanStack AI)

Status: implemented on `feat/ai-runtime`: server read-only vertical (audit steps 1 and 3), write tools with approvals (step 4) and the web chat client (step 5, see [Clients](#clients)). Durable runs (`feat/ai-durable-runs`): on Cloudflare and Node a run executes in its own `AiRun` Durable Object / actor, not in the request that started it (see [Hosting](#hosting)). See [Implementation status](#implementation-status). Source audit: `docs/audits/2026-10-31-tanstack-start-ai.md`.

Verynize chat has two kinds of runtime:

| Runtime                 | Where it runs                                      | Agents                                               | Tools                                                       |
| ----------------------- | -------------------------------------------------- | ---------------------------------------------------- | ----------------------------------------------------------- |
| Local coding agents     | Desktop main process (`desktop/agent-runtime.cjs`) | `claude`, `codex`                                    | Local MCP bridge, shell tools, the agent's own coding tools |
| Model API (`api-model`) | Cloud backend (`cloud/ai.js`, `/api/ai/*`)         | `openrouter` (TanStack AI `@tanstack/ai-openrouter`) | Verynize design tools against a cloud room                  |

The model API runtime does not replace Claude/Codex. It gives the web build (and any signed-in client) a chat that edits shared rooms through the same tool table as the hosted MCP server.

## Ownership of `/api/ai/*`

The cloud backend (`cloud/worker.js`) owns `/api/ai/*` on every target, like the rest of `/api/*`. Start never serves `/api/ai/*`. Reasons: the backend already has the session, room membership, rate limits and per-platform storage on Cloudflare, Node and Vercel, and Start is not deployed on Vercel. No change to `web-start/worker-paths.mjs`, `runWorkerFirst`, or `vercel.json` is needed. `tests/ai-routing.mjs` asserts that `/api/ai/*` reaches the backend on all three targets.

## Credentials

`OPENROUTER_API_KEY` is a server secret (Worker secret / environment variable). It never reaches the browser bundle. Without it, `GET /api/ai/config` reports `enabled: false` and run requests answer 503. Being signed in to Claude Code or Codex says nothing about OpenRouter, and vice versa. The UI shows the two separately. A run obtains its credential through one function, `resolveProvider(env, account, origin)` in `cloud/ai.js`, called once per run from `launchRun` with the run's account (also inside the `AiRun` object, which never stores the key); credentials are moving to per-account keys behind that function.

Optional: `OPENROUTER_BASE_URL` (tests point it at a local fake), `VERYNIZE_AI_MODELS` (comma-separated allowlist `id[=Label]`, first is the default; default `openrouter/auto`), `VERYNIZE_AI_MAX_TURNS` (default 12), `VERYNIZE_AI_MAX_TOOL_CALLS` (default 40), `VERYNIZE_AI_APPROVAL_TIMEOUT_MS` (default 600000, 10 minutes). On Cloudflare the key is a Worker secret (`cf secret put OPENROUTER_API_KEY`) that `cloudflare.config.ts` does not declare, so a deployment without it stays valid.

## HTTP API

All endpoints need a signed-in account (same `accountOf` as the rest of the API: Better Auth cookie/bearer or `X-Verynize-Session`). The account id always comes from the session, never from the request body or the model.

- `GET /api/ai/config` → `{enabled, provider: "openrouter", models: [{id, label}], defaultModel, limits: {maxTurns, maxToolCalls}}`.
- `POST /api/ai/runs` body `{chatId, roomId, prompt, model?, access?: "ask"|"edit"|"auto"|"full", plan?: boolean, helper?: boolean, history?: [{role: "user"|"assistant", text}], designStyle?, idempotencyKey}` → `text/event-stream`. The caller must have at least `viewer` on the room to read and `editor` to write. A repeated `idempotencyKey` for the same account returns the existing run: its stored events are replayed, then the stream follows the run if it is still active (the body of the repeat is ignored; nothing is executed again).
- `GET /api/ai/runs/:runId/events?after=<seq>` → `text/event-stream`: stored events after `seq`, then live events until `done`. Used to reconnect.
- `POST /api/ai/runs/:runId/cancel` → `{ok: true}`. Sets the run's cancel flag; the executor stops before the next model call or tool call and emits `done {stopped: true}`.
- `POST /api/ai/runs/:runId/approvals` body `{requestId, allow, argsHash}` → `{ok: true}`. `argsHash` is the one of the `permission-request`; it is required to approve (optional to deny) and must match the pending call. 400 for a bad body or an approval without `argsHash`, 404 for an unknown run or request, 403 when the run or request belongs to another account, 409 when the request was already decided (replay), the run has ended (or its lease expired), or `argsHash` does not match.

Each SSE message is `data: <json>\n\n` with one event. Idle streams also carry SSE comment lines (`: keep-alive`) every 15 s, which SSE clients ignore.

## Events

Events use the desktop runtime's vocabulary (`desktop/README.md`, `onAgentEvent`), so the chat UI renders both runtimes the same way. Every event is `{id: runId, chatId, seq, type, ...}`, `seq` starting at 1, strictly increasing per run, and stored before it is sent.

| type                   | fields                                                                        |
| ---------------------- | ----------------------------------------------------------------------------- |
| `session`              | `sessionId` (= runId), `agent: "openrouter"`, `model`                         |
| `status`               | `status: "running"\|"awaiting-approval"\|"tool"`                              |
| `assistant-text-delta` | `text`                                                                        |
| `assistant-text`       | `text` (the full text of one assistant message)                               |
| `thinking-delta`       | `text`                                                                        |
| `tool-call`            | `toolCallId`, `name`, `input`                                                 |
| `tool-input-delta`     | `toolCallId`, `delta`                                                         |
| `tool-result`          | `toolCallId`, `name`, `output` (text), `isError`                              |
| `permission-request`   | `requestId`, `toolCallId`, `name`, `input`, `title`, `argsHash`               |
| `permission-resolved`  | `requestId`, `allow`, `reason?` (`"user"`, `"timeout"`, `"cancelled"`)        |
| `usage`                | `inputTokens`, `outputTokens`, `model`                                        |
| `error`                | `message`                                                                     |
| `done`                 | `code` (`"ok"`, `"error"`, `"cancelled"`, `"budget"`), `stopped`, `sessionId` |

## Policy (enforced in the executor, not the prompt)

- Tools come from `toolTable(backend, context)` in `integrations/design-tools.mjs` through the shared cloud backend (`cloud/design-backend.js`, also used by `cloud/mcp.js`): the same definitions and the same `callHostedTool` path as `/api/mcp`, so a write through a run and through hosted MCP produce the same document. Hosted-unavailable tools (`take_screenshot`, `ask_agent`, `import_html`, `export_document`, design preferences, shell tools) are not offered. `create_document` is not offered either: it creates a room outside the run's one room (a scoped backend refuses it anyway). Every other tool is scoped to the run's room (other room ids are refused).
- Read tools (MCP `readOnlyHint`) run freely. Write tools (every other offered tool) need `editor` on the room, checked before the call and again immediately before it runs, after any approval (a member downgraded below editor gets a refusal as the tool result and the run continues; a member removed from the room gets the refusal and the run ends with `error` + `done {code: "error"}`). The room checks the role a third time when it applies the ops.
- `access: "ask"` (the default): every write tool call, once its arguments pass the schema check, raises `permission-request` (with `argsHash`) and `status: "awaiting-approval"`, and waits. The approval is a row in `ai_approval` bound to the account, the run, the tool-call id and `argsHash` (SHA-256 of the tool name and the canonical JSON of the checked arguments, keys sorted). The executor polls the database for the decision, so the approval may reach any instance. It is decided once: approved → the executor re-checks that the approved hash is the hash of the call it is about to run, then the role, then runs it; denied → the model gets the tool result "The user denied this tool call (denied by user); it was not run."; unanswered after `VERYNIZE_AI_APPROVAL_TIMEOUT_MS` (10 minutes) → denied with `reason: "timeout"` (the model gets a timeout denial); run cancelled or ended → denied with `reason: "cancelled"` (cancel ends the run). Each outcome emits `permission-resolved {requestId, allow, reason}`. `edit`/`auto`/`full`: writes run without a prompt (the role checks still apply).
- The approval state never comes from the client's history: the run, its tool calls and approvals are server state. TanStack AI's approval interrupts (`needsApproval`) are not used: they are ephemeral (decisions come back in client-provided history with no replay protection); the executor waits inside TanStack's `onGuardToolCall` middleware hook instead, which sees the checked arguments.
- A write tool call is applied at most once per `(runId, toolCallId)`: it claims its row in `ai_tool_result` before it runs and stores its output after. A repeat (the model reuses a tool-call id, or a request replays a run) gets the recorded result; a claim whose output was never stored (the instance died mid-call) is reported as interrupted and never run again. A repeated `idempotencyKey` and `events?after=` replay stored events and never execute anything.
- `plan: true` (plan first, like the desktop "plan before edits" setting): write tools are offered but every write call is refused with "Plan first: this run only plans…" (no approval is asked, nothing is applied, whatever `access` says), and the system prompt asks for a numbered plan. The user approves the plan by starting a new run without `plan`.
- `helper: true` (like the desktop's read-only helper runs): no write tool is offered and a write call is refused; no approvals.
- Budgets: at most `maxTurns` model turns (TanStack AI `maxIterations`) and `maxToolCalls` tool calls per run (counted by the executor; one turn can call several tools). Exceeding either ends the run with `done {code: "budget"}`.
- Rate limit per account (`AI_LIMIT` binding, same limiter as `MCP_LIMIT`).
- Run, event, approval and tool-result state lives in the backend database (D1 / SQLite / libSQL), not in process memory, so cancel, approval and reconnect work from any instance and the database stays the source of truth for decide-once approvals and at-most-once writes. Where a run is hosted by an `AiRun` object (Cloudflare, Node), the cancel and approval endpoints write the database and then notify the object, which reacts at once; elsewhere (Vercel) the executor polls. A run whose host dies is not continued: it is closed as `done {code: "error"}` once its lease expires (see [Hosting](#hosting)).

## Hosting

Where a run executes, per target:

| Target     | Host of a run                                                                   | Outlives the client          | Approval wait             | Cancel / approval reach the run       | Streams                       |
| ---------- | ------------------------------------------------------------------------------- | ---------------------------- | ------------------------- | ------------------------------------- | ----------------------------- |
| Cloudflare | `AiRun` Durable Object (`env.AI_RUNS`, one per run id, SQLite-backed)           | yes                          | the full timeout (10 min) | notification to the object, immediate | pushed by the object          |
| Node       | the same `AiRun` class as an in-process actor (`cloud/platform/node/actors.js`) | yes (while the process runs) | the full timeout          | notification, immediate               | pushed by the actor           |
| Vercel     | the request that started it (`waitUntil`, request-scoped; no `AI_RUNS` binding) | up to `maxDuration` (300 s)  | about 5 minutes at most   | database flag, polled every second    | database, polled every 400 ms |

How it works where `AI_RUNS` exists (`cloud/ai.js`, `cloud/ai-run.js`, `cloud/ai-host.js`):

- `POST /api/ai/runs`: the Worker authenticates, validates, checks the room role, the per-chat and per-account limits and the idempotency key, and creates the `ai_run` row (D1) exactly as before. It then calls `env.AI_RUNS.getByName(runId).start({runId, accountId, authUserId, origin, input})` and returns an SSE stream subscribed to the object. The prompt and history travel in that call only; the object stores one row (run id, account id, running/done) and no credential.
- The object executes the run with `launchRun` (the same function request-scoped runs use: room role, `resolveProvider`, `executeRun`) under `ctx.waitUntil`. Every event is stored in `ai_run_event` before the object publishes it to its subscribers.
- Streams: `POST /runs` (also an idempotent repeat) and `GET /runs/:id/events?after=` of a running run call the object's `fetch` (`/events?run=&after=`). A subscriber replays the stored events after `after` while buffering live ones, then follows live events (deduplicated by `seq`) until `done`. Any number of subscribers see the same sequence. A finished run is served from the database by the Worker without waking the object. Responses carry `X-Verynize-AI-Stream: object | database | request` (diagnostics).
- Cancel and approvals: the endpoint writes D1 (the cancel flag; the approval decision, decided once with its `argsHash`) and then calls the object's `wake()`. The object reads the cancel flag and aborts the executor (model stream included), and wakes the approval wait, which re-reads its row. If a notification is lost, the alarm re-reads both within 5 s.
- Alarm (every 5 s while the run executes): renews the 30 s lease, re-checks the cancel flag and wakes the approval wait, whose deadline is `VERYNIZE_AI_APPROVAL_TIMEOUT_MS`. On Cloudflare each alarm is an incoming event, so it also resets the object's CPU budget and keeps it from idle eviction; `ctx.waitUntil` and the pending provider fetch hold it in memory meanwhile.
- Reset mid-run (eviction, deploy, crash): the executor and its model stream are gone. The next alarm finds the object's row still running with no executor in memory and closes the run as `error` + `done {code: "error"}` once the lease has expired (at most about 35 s), denying any pending approval. A stream that reaches the object meanwhile follows the database and sees the same close. The run is not resumed: the model stream cannot be resumed, and replaying the turn would meet writes the at-most-once record refuses or reports as interrupted, so ending the run is the honest outcome.
- On Node, `ctx.waitUntil` keeps the actor from the idle sweep while the run executes, and alarms are process timers (not durable: a process restart ends its runs anyway, and the next reader closes them after the lease, as before).
- Vercel stays request-scoped: its actors run one turn at a time on any instance under a Redis lease (`cloud/platform/vercel/actors.js`), which cannot host a minutes-long executor that later requests must reach on the same instance. `cloud/platform/vercel/env.js` leaves out classes marked `static longLived` (`AiRun`), and `cloud/ai.js` falls back to executing in the request when `env.AI_RUNS` is absent.

Open risks:

- **Deploys end running runs.** A Worker deploy resets Durable Objects; runs in flight end with `done {code: "error"}` (about 35 s later) and the user retries.
- **Long runs on Cloudflare** rely on the alarm events for CPU and eviction; a model turn that uses more than 30 s of CPU between two events (not expected: the executor mostly waits on I/O) would get the object reset.
- **Vercel** keeps the request-scoped limits in the table above.
- **At most once, not exactly once** (unchanged): a write interrupted between its claim and its stored result is reported as interrupted, never retried.

## Clients

The chat (legacy runner `web/desktop-panel.js` + chat island `web/src/islands/chat`) runs every turn through one `AgentService` and renders both runtimes with the same transcript, tool cards and approval cards.

- **`AgentService`** (`web/src/lib/agent-service.ts`): `kind` (`desktop` | `web`), `ready()`, `run(options)` → `{id, …}` once the runtime accepted the turn, `cancel(runId)`, `respondPermission({requestId, allow, always?})`, `subscribe(listener)`, `models({agent})`, `discover()`. Events are `{id: runId, chatId, seq, type, …}` in the desktop vocabulary.
  - Desktop: `createDesktopAgentService(window.desktop)` passes calls through to `runAgent`, `cancelAgent`, `respondAgentPermission`, `onAgentEvent`, `listAgentModels`, `discoverAgents` unchanged (`desktop/README.md`).
  - Web: `createWebAgentService(deps)` speaks the HTTP API above. `run` posts `/api/ai/runs` with a new `idempotencyKey` per turn, the open room's id and the chat's earlier turns as `history` (the model API keeps no provider session), and reads the response body as SSE with `fetch` (not `EventSource`: POST plus the session header). The first event names the run. When the stream ends without `done` (network drop, proxy restart), it reconnects with `GET /api/ai/runs/:id/events?after=<lastSeq>` (backoff 0.25–8 s, five tries; before the first event it repeats the POST with the same key, which the server replays) and drops events at or below `lastSeq`. Giving up ends the turn locally with `error` + `done {code: "error"}`. `cancel` posts `/cancel`; `respondPermission` posts `/approvals` with `{requestId, allow, argsHash}` for the run that raised the request, `argsHash` being the one of its `permission-request` (kept with the run id until the request is resolved or the run ends; 409, already decided, is not an error: the run's `permission-resolved` settles the card). `always` is ignored: the model API decides every call on its own, so the approval card has no "Always allow" on the web. Errors of a refused start (400/403/409/429/503) reject `run` with the server's message.
  - Web events gain the desktop field names the runner reads (`normalizeWebEvent`): `tool-call`/`permission-request` → `toolName`, `title`; `tool-input-delta` → `partial`; `tool-result` → `content`; `status`/`error` → `text`; `done.code: "ok"` → `0` and `stopped` for `cancelled`. The server reports each text block twice (deltas, then `assistant-text`); the client drops an `assistant-text` that followed deltas, because on the desktop `assistant-text` means a block that was not streamed.
- **Registration** (`web/src/lib/agent-transport.ts`, `installAgentTransport()` from `web/src/ui.tsx`): `window.verynizePlatform.agents` (`web/platform.js`) holds the service: `provide`, `service()`, `ready()`, `changed()`, `subscribe`. It is deliberately not one of the desktop capabilities (`platform.can("agents")` stays the IPC runtime; `tests/platform-contract.cjs` still checks those against the preload). The desktop registers the IPC service when `can("agents")`; the web always registers the web service, which is `ready()` when the cloud account is signed in on the page's own server and `GET /api/ai/config` (shared query cache, key `["cloud", server, accountId, "ai-config"]`) says `enabled`. Account changes refetch it and notify subscribers; the runner then rebinds its event subscription and re-runs `discover()`.
- **Agent picker**: the runner's `#project-agent` options are the runtime's agents: Claude/Codex on the desktop, only `openrouter` ("OpenRouter") on the web. The model menu shows the server's models (`/api/ai/config` `models`, labels as given) with "OpenRouter default" (the server's `defaultModel`); there is no free-text model id or effort on the web, since the server accepts only its allowlist.
- **Access**: the composer's mode menu (`#agent-access-trigger`: Ask, Edit, Auto, Full access) is shown on the web too and its value is sent as `access` with every run. The chat's default mode is the same as on the desktop (Settings › Agents, `edit` unless changed), so web writes run without a prompt until the user picks Ask; the server's own default (`ask`) applies only to clients that send no `access`.
- **Gate** (`web/src/islands/chat/web-gate.tsx`, `#chat-web-gate[data-state]`), shown on the web instead of the composer while a turn cannot start: `signed-out` "Sign in to use chat" (Sign in button), `not-configured` "Model API not configured on this server", `no-room` "Open or share a cloud room to chat with the model API" (Share button), plus `loading`/`error`. The texts keep the three credentials apart: the Verynize account, the server's OpenRouter key, and Claude Code/Codex sign-ins (desktop only). A running turn keeps the composer so Stop still works.
- **Room**: a web turn targets the room the editor has open (`window.cloudWorkspace.room()`, joined through `#room=` or Files), and only when that room lives on the page's server. `web/cloud-panel.js` fires `cloud-room-changed` when the editor joins or leaves a room, and `window.cloudAccount.fetch(path, init)` gives the transport authenticated raw responses (`X-Verynize-Session`).
- **Desktop-only chat features** stay behind their own capabilities and are hidden on the web: repositories/worktrees (header switcher, `git`), the "+" attach menu, slash commands, dropped/pasted images, MCP tools status, account usage ring, autonomy, design style catalog, second opinion. Steering a running turn falls back to the queue on the web.
- **OpenRouter on the desktop is not offered.** The backend refuses browser requests whose `Origin` differs from its own (`app://verynize` would get 403), so the desktop keeps Claude/Codex only. Offering it would need an explicit allowance for the desktop origin on the server.
- **Node web build** (`web-start/node/server.mjs`): the proxy now sends `X-Forwarded-Host`/`X-Forwarded-Proto` to the backend, so a backend that trusts it (`TRUST_PROXY`) sees the public origin and the model API's same-origin check passes for browser requests. Without `TRUST_PROXY` on the backend, browser chat through the Node web build gets 403.

Verified by `tests/web-ai-chat.mjs` (`npm run test:web`): the Node web build in front of the real backend, Chromium, the provider faked: signed-out and not-configured gates, the room gate, joining through `#room=`, streamed text, a read tool call with the room's content, history on the next turn, a dropped connection resumed with `events?after=`, Stop (server run ends `cancelled`), the model picker, and write approvals with Ask picked in the composer: the approval card shows the call, Allow posts `{requestId, allow, argsHash}` and the artboard lands in the room (backend read and the open canvas) with `permission-resolved {allow: true, reason: "user"}`; Deny leaves the room unchanged and the model's next request carries the denial.

Where the implementation is narrower or more specific than the sections above:

- **Approval waits and host lifetime.** On Cloudflare and Node an approval waits the full `VERYNIZE_AI_APPROVAL_TIMEOUT_MS` (10 minutes) in the run's `AiRun` object with no client connected, and is approved from any request (see [Hosting](#hosting)). On Vercel the run still waits inside the request that started it: Vercel ends a function after `maxDuration` (300 s), so an approval left longer than about five minutes ends the run (closed as `done {code: "error"}` by the next reader; its pending approval is denied with `reason: "cancelled"`). Resuming a run after its host died is not implemented on any target.
- **At most once, not exactly once.** A write whose instance dies after it claimed `(runId, toolCallId)` but before its result was stored is reported as interrupted and never retried; whether the room got the edit is not known to the run.
- **Re-POST with another body.** A repeated `idempotencyKey` follows the stored run; a different prompt, `access`, `plan` or `helper` in the repeat is ignored. `plan` and `helper` are not stored with the run.
- **One room per run.** The backend of a run is scoped to its `roomId`: tools refuse other room ids, `list_documents` shows only that room and `create_document` is not offered. Remote images in `create_artboard`/`import_jsx` are fetched by the server (bounded, as in hosted MCP); that is the only network access of write tools.
- **Extra refusals.** 400 for invalid input (`idempotencyKey` is required), 403 for browser requests from another origin and for runs on a room the caller cannot read, 409 when the chat already has a running turn, 429 when more than three turns of the account are running or `AI_LIMIT` (20 new runs per minute per account) is exceeded.
- **Events.** `usage` is sent once per run with the totals, before `done`. A text block is reported (`assistant-text`) before the tool calls that follow it. `done {code: "budget"}` has no extra `error` event; `stopped` is true only for `cancelled`. Images in tool results are replaced by a text note (only `finish_artboard`, a write tool, returns one among hosted tools).
- **Cancel** reaches an `AiRun`-hosted run at once (the endpoint notifies the object, which aborts the executor), and is also checked before every tool call and on every alarm. A request-scoped run (Vercel) polls the flag once a second. The model stream is aborted with the run's `AbortController`. The provider requests are fetched with that signal directly (`openRouterAdapter`), because on Node the SDK's cloned `Request` does not always follow the original's signal and the stream would stay open until the provider ended it (`tests/cloud-ai-cancel.mjs`).
- **Host lifetime.** Cloudflare and Node: the run executes in its `AiRun` object and keeps going after every client disconnects; a reset object closes its run as `done {code: "error"}` once the 30 s lease expires. Vercel: the run executes inside the request that started it, kept with `waitUntil` up to `maxDuration` (300 s); a run cut off this way is closed as `done {code: "error"}` by the next reader once its lease expires.
- **Auth** is the router's `accountOf`: `Authorization: Bearer` or `X-Verynize-Session`. The Better Auth cookie is not read by `accountOf` today, for these endpoints or the rest of the API.

## Deploy to your Cloudflare account

Checked locally with `npm run deploy:check` (dry run: it lists `env.AI_RUNS (AiRun)` among the bindings). Steps for a real account:

1. **Point the config at your account's resources** (`cloudflare.config.ts`): `domains` (your hostname, or remove it to use `*.workers.dev`), `DB.id` (your D1 database: `npx cf d1 create --name verynize`, then `npx cf d1 list` for the id), the `ASSETS_BUCKET` bucket name, and the email sender (`EMAIL_FROM`, `allowedSenderAddresses`) on a domain onboarded to Email Sending. Keep the Worker name and the Durable Object exports as they are. Workers Paid is required (`limits.cpuMs`).
2. **Sign in**: `npx cf auth login` (or a `CLOUDFLARE_API_TOKEN` with Workers, D1, R2 and Durable Objects edit rights).
3. **Apply the D1 migrations**, including `0005_ai_runs.sql` and `0006_ai_approval_account.sql`: `npm run db:migrate` (`scripts/db-migrate.mjs`, which reads `DB.id` from `cloudflare.config.ts`; `-- --dry-run` checks the arguments first).
4. **Secrets**: `BETTER_AUTH_SECRET` and `ASSET_SIGNING_SECRET` (each `openssl rand -base64 32`) are declared and required on the first upload: put them in a private JSON file and deploy with `npm run deploy -- --secrets-file /path/to/secrets.json`, then delete the file. The model API credential is per account (resolved by `resolveProvider`); until per-account keys land, the runtime is off unless the server key is set: `npx cf workers secrets update OPENROUTER_API_KEY --worker verynize --text '<key>'` (not declared in the config, so deployments without it stay valid). Optional plain variables: `VERYNIZE_AI_MODELS`, `VERYNIZE_AI_MAX_TURNS`, `VERYNIZE_AI_MAX_TOOL_CALLS`, `VERYNIZE_AI_APPROVAL_TIMEOUT_MS`.
5. **Deploy**: `npm run deploy`. `cf deploy` derives Durable Object migrations from the `exports` declarations: the new `AiRun: exports.durableObject({ storage: "sqlite" })` is applied as a `new_sqlite_classes` migration on this deploy; `DesignRoom`, `AccountDirectory` and `PublishedApp` are unchanged. (Wrangler-style `migrations` arrays are not used by this toolchain.)
6. **Check**: sign in on the web app, open a cloud room, send a chat turn; `GET /api/ai/config` reports `enabled: true`, and the run's `POST /api/ai/runs` response carries `X-Verynize-AI-Stream: object`. Close the tab mid-run and reopen the chat: the turn has finished. With Ask access, leave an approval for a few minutes, then allow it.
