# Node capacity measurement — 2026-11-06

## Method

Machine: Apple M1, 8 GiB RAM, macOS, Node 24.15.0, Electron 42.11.18 / Chromium 148.0.7778.280. Base commit: `18fe4f72bf7fcddaee6aaa5c1f73c7872763abea`.

Real Electron, production document API, deterministic mixed frame/text/rectangle/image fixture from `bench-verynize.cjs`. Three fresh profiles per size; benchmark launches within this worktree were sequential. Sibling agents ran tests/builds concurrently; this worktree’s validation began only after the benchmarks. Temporarily lifted both schema limits to 100,000 for measurement. No rendering shortcuts. Tiles remain off for the main measurements. Separate fixed 24-camera zoom trajectory compares tiles OFF/ON with three repeats.

Initial `uptime`: 5:26 uptime, load averages **4.35 / 5.40 / 7.46**. The machine was **measured under contention (load ~3–55); idle rerun pending by lead**: macOS `siriactionsd` consumed approximately one core, plus WindowServer and existing user applications. Those processes were not terminated. Per-run CPU model, memory and load averages are in the raw JSON. Treat these as conservative measurements on this machine, not an uncontended hardware ceiling.

Commands (during temporary lift):

```sh
node eval/canvas-perf/bench-verynize.cjs --sizes 5000,10000,20000,30000,50000 --runs 3 --skip selectAll --no-profile --output eval/canvas-perf/results/node-cap-single-2026-11-06.json
node eval/canvas-perf/bench-verynize.cjs --sizes 5000,10000,20000,30000,50000 --nodes-per-page 5000 --runs 3 --skip selectAll --no-profile --output eval/canvas-perf/results/node-cap-pages-2026-11-06.json
node eval/canvas-perf/bench-tiles.cjs --sizes 5000,10000,20000,30000,50000 --runs 3 --output eval/canvas-perf/results/node-cap-tiles-2026-11-06.json
```

Load is the two-rAF paint fence after the synchronous load call, not a compositor presentation timestamp. Edit is synchronous update time. Handler percentiles pool individual events across the three runs; load/edit/heap are medians of runs. Heap is live JS heap after motion, not total process RSS or peak GPU allocation. Motion runs for two seconds: slow sizes deliver fewer inputs and do not follow identical trajectories. Raw samples retain event counts and frame intervals. All-node selection is omitted because its known cost is unrelated to this decision; it remains an expensive operation. No forced GC.

## Enforcement and error propagation

The single source of truth is `NODE_LIMITS = { perPage: 5000, perDocument: 50000 }` in `web/document-core.js`, exported through both VerynizeDocument and the Node entrypoint. Both validator paths use the same messages. Document counts include every page rather than stopping at the first overflowing partial sum. Errors include actual count, limit, and a split-pages/documents remedy. No node truncation is introduced.

Headless store validation throws; MCP wraps the original message in an `isError` response. Renderer document safety reports the error and retains/recoverably backs up rejected content. Room storage now checks node counts before writing, including counts of unloaded page stubs; room operations return HTTP 413 with the error and rejected count, and the renderer displays `message.error`. Independent byte limits remain unchanged: 20 MiB documents and 2 MiB cloud pages can bind before the node limit.

Repository-wide search covered 10000/5000 and comma-formatted variants. JSX element imports and live layout-bound capture now reference the page constant, as does the component ancestry guard. Tool-coordinate limits, timeouts, operation-batch sizes, font catalogs, scrollback and historical benchmark records are independent and retained.

## Provisional decision and idle rerun

Keep **5,000 nodes per page**, raise the document limit to **50,000 nodes**. The requested 20,000 per page fails badly in these contention measurements: zoom handler p95 37.8 ms and drag p95 10,557 ms. Even 10,000 per page exceeds the zoom budget (20.7 ms). The earlier 5,000-page samples fit all three handler budgets; later contention samples need not. This is a provisional capacity policy, not a 60 Hz guarantee under competing workloads. The 20,000-node design-system import can remain in one document when split across pages. Large whole-document edits and all-node selection remain costly.

**Measured under contention (load ~3–55); idle rerun pending by lead.** Two sibling implementation agents were deliberately running concurrently; the lead requested completion without waiting for them. Every raw sample includes its own load average. The lead should adjust `NODE_LIMITS` after the idle rerun.

Single command from the repository root (dependencies installed):

```sh
node eval/canvas-perf/bench-node-cap.cjs --label idle-2026-11-06
```

This builds the UI, prints uptime, temporarily lifts both limits to 100,000, runs the single-page, split-page and tiles OFF/ON matrices sequentially with three repeats, saves separate JSON files, then restores the exact schema source in a `finally` block. Run it in an otherwise unused worktree; do not edit the schema during measurement. Forced process termination may prevent cleanup: restore the provisional values if that happens. The production application has no runtime cap bypass.

The 50K single-page run loaded in **10,104.7 ms**, edited synchronously in **3,496.5 ms**, then hit the **60,000 ms drag ceiling** on repeat 1. Only 12 pan and 5 zoom events were sampled, so the partial percentiles are descriptive rather than stable estimates. The harness stopped the remaining repeats; no post-motion heap measurement was reached. All other main cells completed three runs. The split layout has 5,000 nodes per page (1, 2, 4, 6 or 10 pages).

**The 50K document cap is provisional capacity, not a measured responsiveness pass.** Split-page drag also fails the budget under contention (p95 4,352.9 ms at 50K; 1,137.4 ms at 20K), and edits traverse the entire document. Keeping pages small is insufficient to eliminate whole-document costs. The lead explicitly requested provisional limits and an idle rerun instead of waiting for sibling agents. Retaining 50K permits the requested import in one document, with these recorded latency limitations; revisit the total cap as well as the per-page cap after the idle rerun.

**Decision: `NODE_LIMITS.perPage` 5,000 → 10,000; `perDocument` stays 50,000.** At 10,000 on one page pan and drag keep 60 Hz and zoom stays near it (34 ms frame p95); from 20,000 zoom frames reach 52 ms and at 30,000 everything degrades. Spread over pages the canvas stays at 60 Hz up to 50,000. The remaining whole-document cost is the edit commit (~1.9 s at 50,000 nodes) — the next performance target, not a canvas limit.
