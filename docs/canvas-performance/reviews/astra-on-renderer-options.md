# Adversarial review: renderer options

**Verdict: retain DOM-first as a provisional engineering recommendation; correct the completeness and timing claims before using this report as a renderer-selection gate.** The saved arithmetic is credible. The experiments compare particular implementations with different quality, caching and completion policies, not backend ceilings.

Read-only review of source, JSON and saved PNG pixels on 2026-11-04. No benchmarks, Electron, browser, installation or build was run. Only this review file was written. Paths below are repository-relative; `P/` means `eval/canvas-perf/prototypes/`, `R` means `eval/canvas-perf/results/prototypes-2026-11-04.json`, and report lines refer to `docs/canvas-performance/renderer-options.md`.

## Findings and required corrections

1. **Wrong: B has 0% incomplete content (lines 41, 53, 205).** `R.results["electron/B/100000"].summary.zoom.incompleteFrac` is **null**, as are A/A2's values. B creates blank placeholders and budgeted work (`P/strategies-dom.js:89–126`), but exposes no `frameStats()` (`:162–164`). The sampler only records that hook (`P/bench.js:31`); the report generator turns missing values into zero (`eval/canvas-perf/bench-prototypes.cjs:171`). This hides both measurable B placeholders and unmeasured compositor checkerboarding. Replace DOM zeros with **not measured**. Instrument visible placeholders separately from raster readiness. The report's assertion that the 60 Hz pass and completeness column account for raster lag (line 33) is false.

2. **Overstated: “real cost of a frame,” “would miss 60 Hz,” “dropped frames,” and edits “land in the next frame” (lines 15, 70–79).** rAF deltas measure callback scheduling/main-thread throughput with pipeline back-pressure, not completed or presented pixels. Disabling vsync does not create a presentation fence. Two rAFs after init/edit (`P/bench.js:65–73,95–103`) provide a paint opportunity, not a guaranteed finished raster/GPU update. `settle()` checks strategy pending work only (`:41–45`); DOM A/A2 have no pending hook, and B can finish mounting before raster finishes. Rename TTFF/edit/fit-all metrics accordingly; call `over25` “rAF intervals >25 ms,” not measured display-drop percentage. A 50 ms interval is also not the same as one dropped refresh. Line 122's ≥55 fps acceptance claim is unsupported by uncapped rAF p95 alone. The baseline document already describes its fence more carefully.

3. **Overstated: 100K speedups compare equivalent workloads.** `P/bench.js:26–36` terminates by wall-clock budget while moving by frame index. In `R.results["electron/A/100000"].raw[*]`, pan contains 21–23 measured intervals, zoom 10–12; A2 drag contains only 3–4. Other strategies complete 60 camera / 40 drag intervals. A therefore never traverses the full zoom-out/back path, and the A2 drag p95 is effectively a tiny-sample maximum. Appendix asterisks disclose truncation, but the headline tables omit it. Keep the ratios as descriptive partial-run ratios, add counts/flags next to headline values, and remove the implication that 86× zoom or ~990× drag is an equivalent full-path improvement. Use fixed camera checkpoints/full trajectories for future comparisons.

4. **Confirmed for these prototypes; unsupported as a GPU/backend conclusion:** D/E's expensive overview and memory (lines 65–66, 116, 121). D is not simply an uncullled strawman: it uses a grid, lazy construction, shared shadow/fill caches, BitmapText and selective masks. However, `P/strategy-pixi.js:137–149` builds full display-object trees to generate every thumbnail; eviction cannot remove visible boards. B draws thumbnails directly through the Canvas painter (`P/strategies-dom.js:99–105`). C/B additionally omit shadows/blur in LOD and replace tiny text with bars (`P/common.js:270–286,311–315`); D generates thumbnails from its full detail tree. This materially favours B/C in overview. At 100K B builds only 254–276 boards, while D builds all for thumbnails before ending at 320 (`R.results["electron/{B,D}/100000"].raw[*].stats`). Pixi also enqueues missing roots again each update (`P/strategy-pixi.js:155–165`), creating duplicate queue bookkeeping. Test direct cached thumbnails, equivalent LOD, deduplicated queues, bounded residency and retained board/tile textures before treating D's costs as inherent to GPU. “Redraws everything each frame even with nothing new” is too broad: stationary clean frames skip rendering (`:210–214`); moving frames redraw the visible scene.

5. **Overstated: C's fast camera numbers establish a smooth, fully rendered win.** The 8 ms budget explicitly accepts stale, fallback or blank tiles (`P/strategy-tiles.js:73–94`); zoom incompleteness is 38.85% at 100K. This is disclosed, but not an equivalent-quality speed comparison. The statistic averages tile-count fractions across callbacks; D uses board-count fractions including overscan, not screen-area fractions. Neither is “percentage of incomplete frames/pixels.” Finer-level fallback can return success with only some child tiles present (`:66–69`), so blanks and usable scaled content are conflated. Record visible-area blank/stale/low-resolution coverage, duration and post-gesture refinement latency. C's costly `dragStart`/`dragEnd` synchronous paints (`:124–126`) are outside the reported drag phase (`P/bench.js:109–114`); report gesture initiation and release latency too.

6. **Confirmed narrowly: A2 models the current free-node camera/edit/drag pattern. Overstated: every drag/edit and a predicted product ceiling (lines 25, 62, 113).** Product `web/canvas-interactions.js:275–285` matches the transform, zoom-dependent promotion and inherited `--iz`; `web/app.js:20–21` creates new ordinary layer elements and rebuilds on render. Free-node moves call render (`web/canvas-interactions.js:832`). Stack drags instead use ghosts/deferred updates (`:790–857`), and text editing has its own live DOM path ending in canonical render (`:720`). A2 also removes whole-page child scans by using precomputed children, not merely the layers-panel rebuild. It omits labels, measurements, subscribers, serialization, selection and product styling. Call A2 a stripped synthetic free-node surrogate, not a validated product performance ceiling. The baseline fixture is different and cannot be subtracted to predict a 1–5 ms product pan.

7. **Confirmed: saved fidelity percentages. Overstated: CSS parity, overview fidelity, and export-gap percentages (lines 87–104, 114–115).** Independently recomputed RGB max-channel thresholds from all six PNG pairs: C 0.79007% / 1.11952%, D 3.35765% / 5.31680%, Dgpu 3.35761% / 5.31648%, E 0.63345% / 2.17631%; A/B exactly zero. These match `R.fidelity["electron/<id>"].diffOver32Pct/diffOver8Pct`. Thresholds are transparent and reproducible (`bench-prototypes.cjs:112–124`), but whole-image percentages dilute localized text errors and ignore alpha. Dimension mismatch would silently compare only the intersection. Actual images are **2600×1676**, not the claimed 2600×1760; raw Electron viewport is **1440×838**, unlike Chrome's 1440×900. Correct effective dimensions.

   C/D/A receive browser-measured world boxes and missing auto-heights before painting (`P/bench.js:131–132`, `P/common.js:143–187`), making this a useful painter test, not independent CSS-layout validation. E also receives this prepass despite the comment saying it measures itself. C does not receive DOM word positions; E measures words itself. One settled 100% fixture proves neither 0% B differences at LOD nor C's “0.8% at overview scale”; no overview-scale pixel audit exists. The proposed tile layer also operates during zoom gestures above overview scale. Measure fractional zoom/DPR, tile-edge blur, auto-layout edits, multilingual shaping and repeated zoom. E's `textBucket` is set only at init (`P/strategy-pixi.js:207`), despite the file header promising zoom-bucket rerasterization. Narrow “BitmapText cannot represent textRuns” to the single-style implementation tested. General native accessibility/export correctness is not established by div rendering or this fixture.

8. **Confirmed as snapshots; overstated as renderer memory requirements (lines 18, 64–66, 235–245).** Memory is sampled after the entire traversal/overview/edit/drag history, once, after GC (`P/bench.js:116–121`). It is not peak or steady-state visible-working-set memory. GPU process working set is not GPU allocation accounting (`bench-prototypes.cjs:67–68`), and heap, renderer and GPU figures must not be added as disjoint allocations. Own texture byte estimates omit overhead; E's `gpuBytes` accumulates allocations without subtracting destroyed/rebuilt text or thumbnails (`P/strategy-pixi.js:83,143,184–219`). Label these policy-dependent snapshots/estimates. Profile cold/warm/overview/after-eviction states, peak process memory and live resource lifetimes separately. Shared-machine load and fixed strategy order (`bench-prototypes.cjs:88–91`) also invalidate an arbitrary ±20% statistical confidence rule; show run ranges and randomize sequential repeats later.

## Recommendation and measurements that could change it

**Confirmed as prioritization, not a measured combined architecture:** first remove product forced-layout loops, repeated scans and global rebuilds; then prototype incremental DOM. This follows the production baseline's attribution and preserves CSS behavior. **Unsupported as a promised performance target:** B+C was not built; its combined memory, synchronization, editing correctness and transition/refinement costs are unknown. “More than about 100K visible layers” is not a measured GPU crossover. FigCraft's retained pixels/damage/LOD support testing avoided work across backends, not declaring Canvas 2D inherently faster; its local renderer benchmarks were unavailable.

Required next measurements, once the lead's current runs finish:

- Capture compositor/raster/presentation evidence and visible-area quality on identical timed camera trajectories; include complete refinement and edit-to-visible pixels.
- Equalize LOD, thumbnail generation, overscan and cache budgets across B/C/D; report cold and warm passes, and full gesture start/end costs.
- Test the actual product after Phase 0/1 with realistic huge single frames, overlapping effects, dense visible text, selection and live previews. Verify stale thumbnails after edits/drags: B deletes thumbnail cache entries but does not immediately replace mounted thumbnails, and drag does not invalidate them (`P/strategies-dom.js:153–162`).
- Build a small B+C integration and audit handoff fidelity/memory before committing to the tile layer. Run randomized isolated repeats and report uncertainty, not a blanket noise threshold.

A GPU implementation winning at matched visible quality, bounded memory and full-path presentation latency would change the deferral recommendation. Conversely, a corrected B meeting actual product budgets would remove the need for Phase 2. Failure of DOM/tile handoffs, text fidelity or dense-scene budgets would justify revisiting retained GPU rendering before any arbitrary node-count threshold.
