# FigCraft canvas performance

> **Validation status.** Architecture claims confirmed line by line in [reviews/sol-on-figcraft.md](reviews/sol-on-figcraft.md), which also corrects two anchors and the transfer advice (applied below). The local benchmark run by the lead is in the section _Local measurement (lead)_ at the end.

Investigated 2026-11-04 (Asia/Jakarta). **FigCraft is a CPU raster renderer presented through a GPU texture, not evidence that a GPU scene renderer wins at 100K mixed layers.** The original investigation could not build it; the lead later built and measured it locally (see the last section).

## Scope and evidence

Cloned latest `main` into the previously absent `/tmp/perf-research/figcraft`; checkout and `git ls-remote origin refs/heads/main` both returned `53ebf1f39c51361282ca55e18c83fbffed2f9a34` (2026-11-03, version 0.15.0). This supersedes the October MCP-only review. Source was read as untrusted data; no upstream scripts, binaries or build scripts were executed. No source/assets were copied into Verynize. The repository declares MIT OR Apache-2.0, but this investigation transfers techniques only.

Labels: **measured** means this investigation; **read-in-code** means static implementation evidence, not runtime verification; **declared-in-README/docs** means upstream statements, including upstream-reported timings; **declared-in-post** means the captured author's claim. Recommendations below are inferences, not performance results.

[crates/render/src/lod.rs:1](https://github.com/storytold/figcraft/blob/53ebf1f39c51361282ca55e18c83fbffed2f9a34/crates/render/src/lod.rs#L1); [crates/render/src/draw.rs:156](https://github.com/storytold/figcraft/blob/53ebf1f39c51361282ca55e18c83fbffed2f9a34/crates/render/src/draw.rs#L156).                                                                                                                                                                                                                                                                                |

[crates/doc/src/geometry.rs:141](https://github.com/storytold/figcraft/blob/53ebf1f39c51361282ca55e18c83fbffed2f9a34/crates/doc/src/geometry.rs#L141).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

## Published numbers, not reproduced

**Declared-in-README/docs:** [docs/hardware-parity.md:26](https://github.com/storytold/figcraft/blob/53ebf1f39c51361282ca55e18c83fbffed2f9a34/docs/hardware-parity.md#L26) attributes these synthetic results to `cargo xtask bench` on the owner's Mac, without a precise machine specification, raw samples or paired Figma/Verynize comparison:

| Upstream workload                           | Upstream-reported result |
| ------------------------------------------- | ------------------------ |
| 50K layers, zoomed-out full render with LOD | ~8 ms                    |
| 10K layers, full 1440×900 render            | 7–15 ms                  |
| 10K layers, one moved layer re-render       | ~0.2 ms                  |
| 50K-layer file save / load                  | ~0.09 s / ~0.16 s        |

The README's sub-millisecond node creation in a 20K-node file concerns **editing**, not frame rendering ([README.md:76](https://github.com/storytold/figcraft/blob/53ebf1f39c51361282ca55e18c83fbffed2f9a34/README.md#L76)). These values cannot support a 100K mixed-scene claim or 60/120 fps guarantee. Conversely, the worker source records a historical browser case with 3.7–4.0 s full renders and 0.7–1.4 s bands ([crates/ui-egui/src/canvas/render_worker.rs:1](https://github.com/storytold/figcraft/blob/53ebf1f39c51361282ca55e18c83fbffed2f9a34/crates/ui-egui/src/canvas/render_worker.rs#L1)): also an upstream report, not a current local measurement, and without a comparable scene specification.

## Other public references

**Silk — declared-in-post, implementation unverified.** The [captured Júlia post](https://x.com/JuliaScript/status/2117561653030158409) describes Effect + Silk WebGPU drawing 100K elements arranged as an XKCD comic. The capture supplies no FPS, frame percentiles, hardware, memory or mixed-text fixture. Targeted web and GitHub searches did not identify a public repository/demo confidently attributable to this Silk; similarly named Silk.NET/shader projects were excluded. The technique is therefore an author-described WebGPU demo, not independently inspected batching/text/culling evidence. No public runnable benchmark was established.

**tldraw experimental canvas — declared-in-post, implementation unverified.** The [captured thread](https://x.com/jesse_vermeulen/status/2117372319211704514) records Steve Ruiz distinguishing his experimental canvas from tldraw's DOM canvas and linking a notes staging worker, but the capture omits the actual worker URL. Searches and the [public repository](https://github.com/tldraw/tldraw) tree did not establish that experiment's source or backend. There is no numerical benchmark in the supplied quote. Do not infer WebGPU, replace production tldraw's architecture with the experiment, or use “until your GPU melts” as a measured result.

**Penpot — read-in-code / declared-in-README/docs.** Public [render-wasm](https://github.com/penpot/penpot/tree/develop/render-wasm) documents Rust compiled with Emscripten and Skia through rust-skia. Its [tile design](https://github.com/penpot/penpot/blob/develop/render-wasm/docs/tile_rendering.md) uses 512×512 logical-screen tiles, shape↔tile indexing, cached Skia images, dirty-region redraw and extra tiles outside the viewport. Tiles are rendered individually; the documentation explicitly does not claim parallel tile scheduling. This is distinct from FigCraft's CPU pixmaps. The inspected primary pages provide no comparable 1K–100K p50/p95 numbers. The [official article](https://penpot.app/blog/penpots-new-rendering-system/) discusses tile rendering; this research did not run Penpot.

## Transfer to Verynize (inference)

Follow [renderer-options.md](renderer-options.md) (incremental DOM first, Canvas 2D tiles for zoom/overview, GPU deferred) and keep the browser as layout oracle and the HTML export contract. (An earlier draft said to keep the Pixi hybrid plan; corrected after review.) Independently implement persistent node identity, changed-subtree invalidation, cached text/layout metrics, effect-aware culling and cached viewport/frame images with bounded overscan. Measure UI selection/layers-panel work separately from painting. Separate camera-only reprojection from content/layout updates; distinguish “old pixels moved smoothly” from “new content finished rendering.” These techniques apply to DOM, Canvas 2D and Pixi; none requires adopting FigCraft code or Rust.

Do not transfer FigCraft's bespoke layout/text engine as if it preserved CSS fidelity. It would replace browser behavior for wrapping, fonts, grid/inline layout, accessibility and editing. Native Rayon gains do not transfer directly to an Electron renderer's JS thread or to its WASM build. LOD bars/splats are useful optional navigation previews but not exact export or full-detail acceptance. GPU texture presentation is not a reason to migrate to WebGPU. The evidence supports profiling and incremental invalidation first; it does not establish a universal DOM layer limit or a measured winning backend for Verynize.

What this establishes:

- **The upstream "~8 ms at 50K with LOD" reproduces** (9.4 ms median here). The same view **without LOD costs 80 ms at 50K and 148 ms at 100K**: the fit-all speed comes from drawing zoomed-out content as colour splats and text bars, not from a faster painter.
- At 100% zoom a full 1440×900 CPU render stays near 3–4 ms from 1K to 100K: culling makes cost depend on what is visible, not on document size. Retained pans cost about 1 ms and a one-layer edit 0.03–5.5 ms.
- Hit testing is a linear scan (16 µs → 236 µs from 1K to 100K), as the review read in code; it is still far under a frame.

What it does not establish:

- These are raster times into a CPU pixmap. Texture upload, GPU presentation, UI work and display are excluded, so they are not frame times and cannot be compared one-to-one with the Electron rAF numbers in [renderer-options.md](renderer-options.md).
- FigCraft's synthetic scene (360×240 screens of about 50 simple layers: rectangles, ellipses, text, auto-layout headers, no images, blur or masks) is lighter per node than the prototypes' artboards (images, shadows, backdrop blur, 40% text). No common scene was run in both.

Comparison that does hold: the closest prototype strategy is **C (tile Canvas 2D)**, which uses the same ideas (cached raster, budgeted refinement, thumbnails when zoomed out). C's fit-all took 948 ms to fully draw at 100K and pans at p95 3.3 ms; FigCraft's LOD fit-all is 16 ms and its retained pan about 1 ms. Most of that gap is the approximation policy (splats and bars vs C's simplified thumbnails) and native multithreaded rasterisation, both of which C could adopt in part (an OffscreenCanvas worker; coarser LOD). It is not evidence for a GPU renderer: FigCraft's document painter is CPU-only.
